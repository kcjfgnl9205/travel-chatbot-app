# 항공권 검색 — 발화에서 말풍선까지

> "오사카 항공권 찾아줘" 한 줄이 들어와서 `listCard` 다섯 줄이 나가기까지.
> 라우터 공통 구조는 [ROUTER.md](./ROUTER.md), 호텔·관광지는 [HOTEL.md](./HOTEL.md) · [ATTRACTION.md](./ATTRACTION.md).

호텔과 모양이 같다 — 같은 제약(5초 예산 · 느린 AI 검색 · 애드픽 rate limit)을 받으므로 같은 모양이 되는 게 맞다. **다른 점만** 이 문서가 다룬다.

가장 큰 차이 셋:

1. **구간이다.** 출발지가 있고, 그게 캐시 키와 카드 머리글에 들어간다
2. **가격이 확정 운임이 아니다.** 실시간 API 가 없어서 "예상가"다
3. **중복 제거를 주소로 못 한다.** 여러 편이 같은 검색 결과 페이지를 가리킨다

---

## 1. 어떤 발화가 항공권으로 오나

### 키워드

```
항공 · 비행기 · 비행편 · 티켓 · 왕복 · 편도
```

**호텔 다음 순서로 본다.** "오사카 항공권이랑 호텔" 은 호텔로 간다.

### 판정은 3단계

| 단계 | 무엇 | 모델 호출 | 예시 |
|---|---|---|---|
| ① 대표 명령어 | `/항공권 오사카` · `항공권 오사카` | **0회** | |
| ② 키워드 + 도시 사전 | 항공 키워드 + 237개 도시표 | **0회** | "오사카 항공권 찾아줘" |
| ③ 모델 | 위 둘로 안 되면 gpt-5-mini | 1회 | "서울에서 오사카 비행기" |

> ⚠️ **출발지를 말하면 ②가 빠진다.** `에서`·`출발` 이 있으면 지명이 둘이라 어느 쪽이 목적지인지 사전으로는 못 가린다. 틀린 지역으로 검색하는 것보다 모델을 한 번 부르는 게 낫다.

### 발화별 파싱 결과

| 발화 | place | from | tripType | 경로 |
|---|---|---|---|---|
| `오사카 항공권 찾아줘` | 오사카 | — → **서울** | `rt` | ② |
| `부산에서 오사카 항공권` | 오사카 | 부산 | `rt` | ③ |
| `오사카 편도 항공권` | 오사카 | — → **서울** | `ow` | ② |
| `오사카 비행기 10월 3일` | 오사카 | — → **서울** | `rt` | ② (`10월 3일` → ignored) |
| `일본 항공권` | 일본 | — | `rt` | ② → **도시 되묻기** |

### 왕복이 기본이다

```
편도 단서: 편도 · 가는 편만 · 원웨이 · one way
```

없으면 **왕복(`rt`)** 으로 본다. 항공권 질문의 대부분이 왕복이기 때문이다.

### ⚠️ 출발지를 말하지 않으면 서울 출발로 본다

되묻지 않는다. 대신 **채웠다는 사실을 카드 아래에 적는다**:

```
서울 출발 기준이에요. 다른 곳이면 "부산에서 출발" 처럼 알려주세요.
```

부산에서 가려던 사람이 고쳐 말할 유일한 단서다. 되묻기보다 결과를 주고 고칠 길을 여는 편이 대화가 덜 끊긴다.

기본값은 `FLIGHT_DEFAULT_ORIGIN_NAME=서울` / `FLIGHT_DEFAULT_ORIGIN_CODE=ICN`.

## 2. 발화 → 응답 전체 흐름

```
"@여행메이트 오사카 항공권 찾아줘"
  │
  │  ── 카카오 5초 예산 안 ─────────────────────────────
  │
  ├─ 의도·지명 추출            → intent=flight, place=오사카, from=null
  ├─ 지역 정규화 (도착지)      "오사카" → place_id=42, iata=KIX
  ├─ 지역 정규화 (출발지)      말 안 했으면 "서울" → place_id=7, iata=ICN
  │                            originAssumed=true → 고지에 반영
  ├─ 캐시 조회                 flight:7>42:rt
  │    ├ 히트 → listCard 즉시 ✅
  │    └ 미스 → pending 선점 → 아래로
  │
  │  ── 백그라운드 ────────────────────────────────────
  │
  ├─ provider 검색             gpt-5-mini 2단 + 웹 검색 (7~30초)
  ├─ 중복 제거                 편명+출발시각 기준 (주소 아님!)
  ├─ search_results 에 20건 저장 (TTL 6시간)
  └─ 카드 조립 → callbackUrl 로 POST
```

**출발지 IATA 가 여기서 값을 한다.** 도시 사전([city-table.ts](../src/modules/places/city-table.ts))에 있는 도시는 공항 코드가 딸려 오고, 그게 검색 프롬프트의 `인천(ICN) → 오사카(KIX)` 가 된다. 모델 경로로 등록된 도시에는 없을 수 있다.

## 3. 상황별로 무엇이 나가나

호텔과 같다. 주어만 `서울→오사카 항공권` 으로 바뀐다.

| 상황 | 실제 문구 |
|---|---|
| 미스 + 콜백 켜짐 | `서울→오사카 항공권을 찾고 있어요. 잠시만요 🔍` |
| 미스 + 콜백 꺼짐 | `서울→오사카 항공권을 찾고 있어요 🔍`<br>`30초쯤 뒤에 다시 물어봐 주세요!` |
| 남이 검색 중 | `서울→오사카 항공권을 먼저 찾고 있어요 🔍` |
| 결과 0건 | `서울→오사카 항공권 정보를 지금은 정리하지 못했어요 🙏` |
| 검색 실패 | `서울→오사카 항공권을 불러오지 못했어요 🙏` |
| 키가 없어 불가 | `지금은 서울→오사카 항공권 검색이 안 되고 있어요 🙏` |
| 나라를 말함 | `일본 어느 도시의 항공권을 찾을까요?` |

> 도시 고르기 카드에서 줄을 누르면 **출발지까지 박힌 문장**이 전송된다 — `서울에서 도쿄 항공권 찾아줘`. 그러면 "서울 출발 기준이에요" 안내가 필요 없어지고, 부산에서 가려는 사람은 그 문장을 고쳐 보내면 된다.

## 4. 카드 한 장 해부

### ⚠️ `listCard` 다. `itemCard` 가 아니다

예전에는 `itemCard` 캐러셀이었다. **그룹챗봇이 itemCard 를 못 그린다** — 팀톡방에서 항공권만 말풍선이 통째로 사라졌다. 로그는 200 인데 화면은 빈칸이었다.

정보 밀도를 잃더라도 **보이는 카드가 낫다.** 상세는 줄 링크로 넘긴다.

같은 실패 방식을 한 번 더 겪었다 — 버튼의 `action: "talk_mention"`(문서에 없는 값)을 썼더니 응답 전체가 렌더링되지 않아 카드까지 같이 사라졌다. **카카오는 스킬 응답을 말풍선 단위가 아니라 통째로 검증한다.**

### 실제 JSON

```json
{
  "version": "2.0",
  "template": {
    "outputs": [
      { "listCard": {
          "header": { "title": "서울→오사카 항공권 5편" },
          "items": [
            { "title": "대한항공 KE723 · 325,000원",
              "description": "10/3(토) 09:20 ↔ 10/7(수) 12:30 · 직항",
              "link": { "web": "https://bot.nolmoa.com/r/Kq7mZ1vTx8Bd" } }
          ],
          "buttons": [
            { "label": "더 보기", "action": "block", "blockId": "...",
              "messageText": "오사카 항공권 더 보기",
              "extra": { "cache_key": "flight:7>42:rt", "offset": 5 } }
          ] } },
      { "simpleText": { "text": "서울 출발 기준이에요. 다른 곳이면 \"부산에서 출발\" 처럼 알려주세요." } }
    ],
    "quickReplies": [
      { "label": "도쿄 항공권", "action": "message", "messageText": "도쿄 항공권 찾아줘" },
      { "label": "후쿠오카 항공권", "action": "message", "messageText": "후쿠오카 항공권 찾아줘" }
    ]
  }
}
```

**썸네일이 없다.** 항공권에는 보여줄 사진이 없다.

### 머리글

| 페이지 | 문구 |
|---|---|
| 1페이지 | `서울→오사카 항공권 5편` |
| 2페이지부터 | `서울→오사카 항공권 6~10번째` |

### 한 줄의 제목·설명 — 여기가 호텔과 제일 다르다

```
title        항공사 + 편명 · 가격        (40자)
description  일정 · 소요/경유            (40자 1줄)
```

**가격을 제목에 둔다.** 항공편을 고르는 첫 번째 축이고, `listCard` 에서 제목이 설명보다 눈에 먼저 들어온다.

[`listRowDescription()`](../src/modules/flight/flight.types.ts) 은 편도/왕복이 다르다:

| | 예시 | 무엇을 넣나 |
|---|---|---|
| 편도 | `10/3(토) 09:20→11:45 · 2시간 25분 · 직항` | 날짜·출발·도착·소요·경유 |
| 왕복 | `10/3(토) 09:20 ↔ 10/7(수) 12:30 · 직항` | 두 구간의 날짜·출발 + 경유 |

> ⚠️ **왕복은 도착 시각과 소요 시간을 버린다.** 두 구간의 날짜·출발 시각만으로 40자가 거의 찬다. 대신 **직항 여부는 남긴다** — 경유가 몇 번인지가 시각 다음으로 중요한 판단 기준이고, 예약 페이지를 열기 전에 알아야 거를 수 있다.
>
> 그래서 왕복에서는 경유지 **이름**을 먼저 버린다(`1회 경유 (홍콩)` → `1회 경유`). 40자를 넘기면 잘리는데, 잘리면 가장 뒤에 있는 직항 여부가 사라지기 때문이다.

### 시각은 `HH:MM` 문자열이다

`Date` 로 만들지 않는다. 항공편 시각은 **각 공항의 현지 시각**인데, `Date` 로 만들려면 시간대를 붙여야 하고 모델은 그걸 못 준다. **잘못된 시간대로 변환된 시각은 시각을 안 보여주는 것보다 나쁘다.**

모델은 `09:20 (현지)`, `오전 9시 20분`, `9:20 AM` 을 섞어서 준다. 읽어낼 수 있으면 정규화하고, 못 하면 버린다.

날짜 요일도 UTC 자정으로 파싱한다 — 지역 시간대로 파싱하면 서버가 어디에 떠 있는지에 따라 요일이 하루씩 밀린다.

## 5. ⚠️ 가격은 확정 운임이 아니다

**항공 운임은 실시간이고 우리는 실시간 API 가 없다.** 웹 검색으로 얻는 건 "그 노선이 대략 얼마인가" 이지 지금 살 수 있는 가격이 아니다.

여기를 정확한 운임처럼 포장하면 **사용자는 카드 가격을 믿고 눌렀다가 배신당한다.** 실제 금액은 예약 페이지에서 확인하게 만든다.

GDS·항공사 API 가 붙으면 provider 를 갈아끼우면 된다 — 그래서 `FLIGHT_PROVIDER` 토큰으로 주입한다.

### 날짜를 검색에 넘기지 않는다

캐시를 **노선·왕복여부로만** 가르기 때문이다. 날짜를 안 주면 모델은 되묻거나 임의의 날짜를 지어내므로, 프롬프트에 못 박는다:

```
특정 날짜가 정해지지 않았으니 최근 한 달 기준의 일반적인 요금대를 조사한다.
날짜를 지어내지 말고, 확인된 날짜가 없으면 날짜 필드는 null 로 둔다.
```

사용자가 날짜를 말했으면 그건 `ignored` 로 옮겨져 카드 아래 고지에 적힌다.

## 6. 결과는 어떻게 만들어지나

[`OpenAiFlightProvider`](../src/modules/flight/providers/openai.provider.ts) — 호텔과 같은 2단 구조. 뼈대는 [`TwoStageSearch`](../src/modules/openai/two-stage.ts) 를 공유한다.

```
1차  web_search 로 후보 30편 수집          (구조화 JSON)
2차  가격·소요시간·경유·출발시각 비교 → 20편 (구조화 JSON)
```

썸네일 단계가 없다.

### 예약 링크 — **두 곳만** 인정한다

```
trip.com · myrealtrip.com
```

호텔은 네 곳인데 여기는 둘이다. **클룩·호텔스닷컴은 항공권을 팔지 않아서** 허용해두면 모델이 "항공권 링크"라며 엉뚱한 페이지를 가져온다. 반대로 이 두 곳은 호텔 쪽에서 이미 애드픽 변환이 되는 게 확인돼 수익화 경로가 검증돼 있다.

스카이스캐너·네이버항공권·항공사 자체 사이트도 프롬프트에서 명시적으로 막는다.

> ⚠️ 허용 호스트를 바꾸면 **프롬프트 문구도 같이** 바꿔야 한다. 모델에게 A 를 찾으라고 시켜놓고 B 만 통과시키면 결과가 전부 버려진다. 그래서 목록과 문구를 같은 파일에서 만든다.

### 중복 제거 — 편명 + 출발시각

```ts
flightKey(f) = [편명 ?? 항공사, 출발공항, 도착공항, 출발일, 출발시각].join('|')
```

> ⚠️ **호텔처럼 `sourceUrl` 로 판정하면 안 된다.** 항공권은 여러 편이 같은 **노선 검색 결과 페이지**를 가리키므로, 주소로 중복을 지우면 카드가 한 줄만 남는다.

그래서 `sourceUrl` 은 항공편의 신원이 아니다. 다만 애드픽 변환의 입력이기는 해서, 주소가 겹치는 만큼 **변환 호출 수가 줄 수보다 적다** — rate limit 측면에서는 이득이다.

### 모델 출력을 못 믿는 자리들

| 필드 | 정규화 |
|---|---|
| 공항 코드 | 영문 3자만 통과. 없으면 쿼리 값으로 채운다 (검색 자체가 그 노선으로 나갔으므로 쿼리가 더 믿을 만하다) |
| 편명 | `ke 723` → `KE723`. dedupe 키라 표기를 통일해야 한다 |
| 시각 | `HH:MM` 만. 오전/오후·AM/PM 을 읽어 24시로 |
| 경유 횟수 | **0 이 유효한 값이다** (직항). `positiveInt` 로 거르면 직항이 전부 사라진다 |
| 날짜 | `2026-02-30` 같은 값은 `Date` 가 3월 2일로 조용히 굴린다. 되돌려 보고 같은지 확인한다 |

## 7. 캐시와 비용

| 무엇 | 어디 | TTL |
|---|---|---|
| 검색 결과 20건 | `search_results` + 메모리 | **6시간** |
| 실패·빈손 | 같음 | 10분 |

**TTL 이 호텔(24시간)보다 짧다.** 운임이 제일 빨리 변하기 때문이다. 관광지는 30일이다.

### 캐시 키에 축이 셋 있다

```
flight:{출발 place_id}>{도착 place_id}:{rt|ow}
```

> ⚠️ **출발지·도착지·왕복여부가 모두 들어가야 한다.** 지역만으로 잡으면 왕복을 물은 사람에게 편도 결과가 나간다.

**날짜·인원은 넣지 않는다.** 넣으면 캐시가 거의 안 맞아 매 질문이 AI 호출이 된다.

## 8. DB 에 남는 것

노출 한 줄은 호텔과 같은 공통 테이블에 들어가고, 항공권 고유 값은 `recommendation_item_flights` 로 간다 (0007).

| 컬럼 | 호텔 | 항공권 |
|---|---|---|
| `recommendations.city_slug` | 도시 | **도착지** |
| `recommendation_items.item_name` | 항목명 | **`대한항공 KE723 ICN→KIX`** |
| 가격 | `..._hotels.price_per_night` (1박) | `..._flights.price_total` (**1인 총액**) |
| 썸네일 | `..._hotels.image_url` | 칸이 없다 (카드에 이미지가 없다) |
| 항공권 고유 | — | `airline` · `stops` · `cabin` · `duration_minutes` |

담기는 건 "노출된 항목의 이름"이다. 나중에 로그에서 알아볼 수 있게 항공사·편명·구간을 합쳐 넣는다 (0007 전에는 `hotel_name` 이었다).

## 11. 알려진 한계

- **확정 운임이 아니다** (5절). 실시간 API 를 붙이기 전까지는 참고용이다
