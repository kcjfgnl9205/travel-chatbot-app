# 항공권 검색 — 발화에서 말풍선까지

> "오사카 항공권 찾아줘" 한 줄이 들어와서 `listCard` 다섯 줄이 나가기까지.
> 라우터 공통 구조는 [ROUTER.md](./ROUTER.md), 호텔·관광지는 [HOTEL.md](./HOTEL.md) · [ATTRACTION.md](./ATTRACTION.md).

라우터·캐시·카드 조립은 호텔과 같은 길을 쓴다. **다른 점만** 이 문서가 다룬다.

가장 큰 차이 셋:

1. **⚠️ 검색하지 않는다.** 모델을 부르지 않고 플랫폼 검색 페이지를 열어준다 (§2)
2. **가격 숫자가 없다.** 그 대가로 즉답·0원·날짜 반영을 얻었다
3. **구간이다.** 출발지가 있고, 그게 카드 머리글과 공항 선택에 들어간다

> 모델에게 시세를 묻던 경로는 **지웠다.** 설정으로 되돌리는 길도 없다 — 되살리려면
> git 기록에서 꺼내야 한다(`fix: 트립닷컴은 공항이 아니라 도시 코드를 받는다` 이전).
> 다시 숫자를 넣고 싶어지면 요청 경로가 아니라 **미리 채워두는 표**가 맞다 (§5).

---

## 1. 어떤 발화가 항공권으로 오나

### 키워드

```
항공 · 비행기 · 비행편 · 티켓 · 왕복 · 편도
```

**호텔 다음 순서로 본다.** "오사카 항공권이랑 호텔" 은 호텔로 간다.

### 판정은 3단계

| 단계 | 무엇 | 모델 호출 | 예시 |
|---|---|---|---|
| ① 대표 명령어 | `/항공권 오사카` · `항공권 오사카` | **0회** | |
| ② 키워드 + 도시 사전 | 항공 키워드 + 237개 도시표 | **0회** | "오사카 항공권 찾아줘" |
| ③ 모델 | 위 둘로 안 되면 gpt-5-mini | 1회 | "서울에서 오사카 비행기" |

> ⚠️ **출발지를 말하면 ②가 빠진다.** `에서`·`출발` 이 있으면 지명이 둘이라 어느 쪽이 목적지인지 사전으로는 못 가린다. 틀린 지역으로 검색하는 것보다 모델을 한 번 부르는 게 낫다.

### 발화별 파싱 결과

| 발화 | place | from | tripType | 경로 |
|---|---|---|---|---|
| `오사카 항공권 찾아줘` | 오사카 | — → **서울** | `rt` | ② |
| `부산에서 오사카 항공권` | 오사카 | 부산 | `rt` | ③ |
| `오사카 편도 항공권` | 오사카 | — → **서울** | `ow` | ② |
| `오사카 비행기 10월 3일` | 오사카 | — → **서울** | `rt` | ② (`10월 3일` → ignored) |
| `일본 항공권` | 일본 | — | `rt` | ② → **도시 되묻기** |

### 왕복이 기본이다

```
편도 단서: 편도 · 가는 편만 · 원웨이 · one way
```

없으면 **왕복(`rt`)** 으로 본다. 항공권 질문의 대부분이 왕복이기 때문이다.

### ⚠️ 출발지를 말하지 않으면 서울 출발로 본다

되묻지 않는다. 대신 **채웠다는 사실을 카드 아래에 적는다**:

```
서울 출발 기준이에요. 다른 곳이면 "부산에서 출발" 처럼 알려주세요.
```

부산에서 가려던 사람이 고쳐 말할 유일한 단서다. 되묻기보다 결과를 주고 고칠 길을 여는 편이 대화가 덜 끊긴다.

기본값은 `FLIGHT_DEFAULT_ORIGIN_NAME=서울` / `FLIGHT_DEFAULT_ORIGIN_CODE=ICN`.

### ⚠️ 서울은 공항이 둘이다 — 국내선은 김포, 국제선은 인천

사전은 서울의 대표 공항을 인천(ICN) 하나로 들고 있다. 그대로 쓰면 "제주 항공권" 이
`ICN → CJU` 로 나가서, 편수가 몇 배인 김포 노선을 통째로 못 보여준다.

그래서 **노선이 국내선이면 서울 쪽 끝을 김포(GMP)로 바꾼다**
([airports.ts](../src/modules/flight/airports.ts)).

| 발화 | 노선 |
|---|---|
| "제주 항공권" | `GMP → CJU` |
| "오사카 항공권" | `ICN → KIX` |
| "서울에서 제주" | `GMP → CJU` |
| "인천에서 제주" | `ICN → CJU` (공항을 콕 집었다) |
| "부산에서 서울" | `PUS → GMP` (도착지도 같이 내린다) |

바꾸는 건 **공항 코드뿐**이다. 도시명은 "서울" 그대로라 고지("서울 출발 기준이에요")도
캐시 키(place id)도 그대로다. 같은 (출발지, 도착지) 쌍이면 코드도 매번 같으므로 캐시가
갈리지 않는다.

⚠️ **국내인지 모르면 인천이다.** 국내인 줄 몰라 인천으로 나가면 "노선이 적다" 지만,
해외인데 김포로 나가면 노선이 아예 없는 공항으로 검색이 나간다.

## 2. ⚠️ 항공권은 검색하지 않는다

**줄 링크는 어차피 우리가 만든다.** 모델이 주는 주소는 빈 검색 폼이라 쓰지 않고, IATA 코드로 세 플랫폼의 주소를 직접 조립한다([search-url.ts](../src/modules/flight/search-url.ts)). 그러면 모델이 실제로 사오는 건 카드 한 줄뿐이다:

```
트립닷컴에서 보기
32~48만원대 · 직항 1시간 55분 · 진에어          ← 모델이 7~30초·요금을 들여 사온 전부
```

그 셋 중 **직항 여부·소요시간·항공사는 노선의 거의 고정 사실**이다. 진짜로 변하는 건 가격 하나고, 그것조차 "웹에서 본 값의 폭" 이라 확정 운임이 아니라고 고지하고 나간다.

그래서 그 한 줄을 포기했다([link-offers.ts](../src/modules/flight/link-offers.ts)).

| | 얻는 것 | 잃는 것 |
|---|---|---|
| 응답 | **즉답** — 5초 예산 안, "찾고 있어요" 도 콜백도 없다 | |
| 비용 | **0원** — 단톡방에서 몇 번을 물어도 공짜 | |
| 실패 | **빈손이 없다** — 모델이 이유 없이 빈손으로 돌던 모드가 사라졌다 | |
| 조건 | **날짜·인원을 반영한다** — 캐시를 노선으로 가를 이유가 없어졌다 | |
| 가격 | | **플랫폼별 가격 비교.** 어디가 싼지가 줄을 고르는 기준이었다 |

가격이 빠진 자리는 플랫폼이 서로 어떻게 다른지로 채운다. 조사가 필요 없는 사실이다:

```
트립닷컴에서 보기        그 자리에서 예약·결제까지
스카이스캐너에서 보기    여러 예약처 가격을 한 번에 비교
마이리얼트립에서 보기    한국어 고객센터 · 원화 결제
```

> 시세를 **미리 채워두는 표**(하루 한 번 배치)를 나중에 얹으면 요청 경로는 그대로 두고 이 줄 위에 숫자만 올릴 수 있다. 그때도 이 경로가 기반이다.

### 전체 흐름

```
"@가자고 제주 항공권 10/20~24 4명"
  │
  │  ── 카카오 5초 예산 안. 여기서 끝난다 ──────────────
  │
  ├─ 의도·지명 추출            → intent=flight, place=제주, from=null
  ├─ 지역 정규화 (도착지)      "제주" → place_id=51, iata=CJU
  ├─ 지역 정규화 (출발지)      말 안 했으면 "서울" → place_id=7
  ├─ 공항 결정                 국내선이라 서울 쪽은 GMP (§1 의 두 공항)
  ├─ peek()                    플랫폼 3곳의 주소 조립 — AI 호출 0회
  ├─ 날짜·인원                 발화에서 읽는다 → 10/20, 10/24, 4인
  └─ listCard 즉시 ✅
```

**출발지 IATA 가 여기서 값을 한다.** 도시 사전([city-table.ts](../src/modules/places/city-table.ts))에 있는 도시는 공항 코드가 딸려 온다. 공항이 없는 도시(교토·강릉)는 노선을 특정할 수 없어 **줄을 아예 만들지 않는다** — 빈 검색 폼으로 보내느니 "못 찾았어요" 가 낫다.

### 날짜·인원은 발화에서 읽는다

[trip-params.ts](../src/modules/flight/trip-params.ts). **모델을 부르지 않는다.**

| 발화 | 출발 | 귀국 | 인원 |
|---|---|---|---|
| `제주 10/20~24 4명` | 10/20 | 10/24 | 4 |
| `제주 11월 3일 가서 7일에 와` | 11/3 | 11/7 | 1 |
| `제주 20일에 출발` (날짜 하나) | 11/20 | **+7일** | 1 |
| `다낭 3박 4일 3명` | 내일 | **+3박** | 3 |
| `오사카 다음 주 금요일 편도 2명` | 다음 주 금 | — | 2 |
| `부산 오사카 다음주 수요일~금요일` | 다음 주 수 | 다음 주 금 | 1 |
| `오사카 다음 달 15일` | 다음 달 15 | +7일 | 1 |
| `오사카 2주 뒤` | +14일 | +7일 | 1 |
| `후쿠오카 11월 첫째주` | 11/1 | +7일 | 1 |
| `제주 토요일 당일치기` | 토 | **같은 날** | 1 |
| `후쿠오카 항공권` | **내일** | **+7일** | **1** |

⚠️ **요일 범위는 뒤쪽이 앞쪽 주를 물려받는다.** "다음주 수요일~금요일" 의 금요일을 따로 세면 이번 주 금요일이 되어 **귀국일이 출발일보다 앞선다** — 실제로 10/21 출발 · 10/16 귀국으로 나갔다. 같은 이유로 "다음 달 15일" 도 한 덩어리로 읽는다.

⚠️ 그래도 거꾸로 선 일정이 만들어지면 **기본값(+7일)으로 되돌린다**(`resolveTrip`). 파서가 어디선가 틀려도 거꾸로 된 링크는 안 나간다. 당일치기(박수 0)는 같은 날이라 여기 안 걸린다.

규칙은 이렇다. **날짜가 하나면 출발일**이고, 왕복인데 귀국일이 없으면 **출발일로부터 7일 뒤**다. 연도 없는 날짜가 이미 지났으면 내년으로 굴린다.

⚠️ **파서가 틀려도 손해가 작다는 것이 이 설계의 전제다.** 우리가 여는 건 *검색 폼이 채워진 페이지*지 예약 확정이 아니다. 10/20 을 잘못 읽으면 사용자가 그 페이지에서 고치면 되고, 아무것도 안 넣어 내일 날짜로 여는 것보다 낫다. **가격을 틀리는 것과는 성격이 다르다** — 그래서 완벽하지 않은 규칙으로 충분하고, 모델을 부를 이유가 없다.

⚠️ **읽은 날짜를 어디에도 저장하지 않는다.** 의도 파싱 결과는 발화 해시로 7일간 캐시되고(`INTENT_CACHE_TTL_MINUTES`), 검색 행은 모두가 공유하며 6시간 산다. 둘 중 어디에 절대 날짜를 구워 넣어도 **남의 날짜가 내 링크로 나온다.** 그래서 카드를 그리는 순간 그 사람의 발화에서 다시 읽는다 — 링크 날짜를 저장하지 않는 것과 같은 이유다(0004).

⚠️ **반영한 조건은 고지에서 뺀다.** 날짜를 링크에 넣어놓고 "날짜는 반영되지 않았어요" 라고 적으면 맞는 링크를 받고도 틀렸다고 읽는다. 다만 고지용 파서와 여기가 발화를 다르게 끊으므로("다음 주" vs "다음 주 금요일"), **우리가 읽은 표현에 포함되면** 뺀다.

## 3. 상황별로 무엇이 나가나

**항공권에는 "찾고 있어요" 가 없다.** 검색을 안 하므로 기다릴 일이 없고, 콜백도 안 쓴다. 호텔·관광지와 제일 크게 갈리는 지점이다.

| 상황 | 실제 문구 |
|---|---|
| 평소 | **카드 즉시** |
| 공항을 모르는 지역 (교토·강릉) | `서울→교토 항공권 정보를 지금은 정리하지 못했어요 🙏` |
| 나라를 말함 | `일본 어느 도시의 항공권을 찾을까요?` |

공항이 없는 지역은 노선을 특정할 수 없어 **줄을 아예 안 만든다** — 빈 검색 폼으로 보내느니 못 찾았다고 말하는 편이 낫다.

> 도시 고르기 카드에서 줄을 누르면 **출발지까지 박힌 문장**이 전송된다 — `서울에서 도쿄 항공권 찾아줘`. 그러면 "서울 출발 기준이에요" 안내가 필요 없어지고, 부산에서 가려는 사람은 그 문장을 고쳐 보내면 된다.

## 4. 카드 한 장 해부

### ⚠️ `listCard` 다. `itemCard` 가 아니다

예전에는 `itemCard` 캐러셀이었다. **그룹챗봇이 itemCard 를 못 그린다** — 팀톡방에서 항공권만 말풍선이 통째로 사라졌다. 로그는 200 인데 화면은 빈칸이었다.

정보 밀도를 잃더라도 **보이는 카드가 낫다.** 상세는 줄 링크로 넘긴다.

같은 실패 방식을 한 번 더 겪었다 — 버튼의 `action: "talk_mention"`(문서에 없는 값)을 썼더니 응답 전체가 렌더링되지 않아 카드까지 같이 사라졌다. **카카오는 스킬 응답을 말풍선 단위가 아니라 통째로 검증한다.**

### 실제 JSON

```json
{
  "version": "2.0",
  "template": {
    "outputs": [
      { "listCard": {
          "header": { "title": "서울→오사카 항공권" },
          "items": [
            { "title": "트립닷컴에서 보기",
              "description": "그 자리에서 예약·결제까지",
              "link": { "web": "https://bot.nolmoa.com/r/Kq7mZ1vTx8Bd" } }
          ],
          "buttons": [] } },
      { "simpleText": { "text": "링크는 10월 21일 출발 · 10월 23일 귀국 · 4인으로 검색돼요." } },
      { "textCard": {
          "description": "가자고에게 이어서 말하기",
          "buttons": [ { "label": "@가자고", "action": "mention" } ] } }
    ]
  }
}
```

**줄 하나가 편이 아니라 플랫폼 하나다** (§6). 플랫폼이 셋뿐이라 **"더 보기" 버튼이 없다.** 세 번째 말풍선의 `mention` 버튼은 입력창에 `@봇이름` 을 넣어준다 — 팀채팅 챗봇은 퀵리플라이를 지원하지 않아서 누를 것이 이것뿐이다.

**썸네일이 없다.** 항공권에는 보여줄 사진이 없다.

### 머리글

| 페이지 | 문구 |
|---|---|
| 1페이지 | `서울→오사카 항공권 5편` |
| 2페이지부터 | `서울→오사카 항공권 6~10번째` |

### 한 줄의 제목·설명

```
title        {플랫폼}에서 보기        어디로 보내는 줄인지가 제목이다
description  플랫폼의 성격 한 줄      고를 단서. 조사해야 아는 값이 아니다
```

```
트립닷컴에서 보기        그 자리에서 예약·결제까지
스카이스캐너에서 보기    여러 예약처 가격을 한 번에 비교
마이리얼트립에서 보기    한국어 고객센터 · 원화 결제
```

⚠️ **설명을 비우면 세 줄이 똑같아 보인다.** 제목이 전부 "…에서 보기" 라 고를 단서가 사라진다. 모르는 플랫폼은 빈 줄로 두고 **지어내지 않는다.**

**썸네일이 없다.** 항공권에는 보여줄 사진이 없다.

---

## 5. ⚠️ 가격이 없다

**카드에 금액이 한 줄도 없다.** 조사하지 않기 때문이다(§2). 대신 줄 설명에 플랫폼의 성격을 적어 고를 단서를 준다.

그래서 "확정 운임이 아니다" 같은 고지도 하지 않는다 — **할 말이 없는 것이 가장 정직하다.** 금액은 사용자가 도착한 예약 페이지가 답한다.

> 시세를 보여주고 싶어지면 **요청 경로가 아니라 미리 채워두는 표**로 하는 게 맞다. 하루 한 번 배치로 인기 노선을 훑어 두면, 링크 카드 위에 숫자만 얹으면서 즉답은 그대로 유지된다. 요청마다 모델을 부르던 예전 방식으로 돌아가면 7~30초와 요금이 같이 돌아온다.

## 6. 예약 링크 — **세 곳만** 보낸다

```
트립닷컴(kr.trip.com) · 스카이스캐너(skyscanner.co.kr) · 마이리얼트립(air-web.myrealtrip.com)
```

주소는 [search-url.ts](../src/modules/flight/search-url.ts) 가 조립한다. **형식을 아는 곳만 넣는다** — 실제로 검색해서 주소창을 복사한 형식만이고, 지어내지 않는다. 넷째가 생기면 같은 절차를 밟는다.

⚠️ **파라미터 이름을 추측하면 조용히 틀린다.** 세 번 당했다:

| 증상 | 원인 |
|---|---|
| 4명으로 물었는데 **1명**으로 열림 | 스카이스캐너는 `adults` 가 아니라 `adultsv2` |
| 〃 | 트립닷컴은 `quantity` 와 함께 `searchboxarg=t` 가 있어야 읽는다 |
| 도쿄를 눌렀는데 **부산**이 열림 | 트립닷컴 `dcity`/`acity` 는 공항이 아니라 **도시 코드**(sel·tyo) |

전부 **빈 폼보다 나쁘다.** 사용자는 틀린 줄 모르고 예약을 진행하다 가격이 달라서야 안다. 그래서 복사한 주소의 **파라미터 키 목록 전체**를 테스트에 박아뒀다.

> 부산(PUS)·하노이(HAN)·제주(CJU)는 공항 코드와 도시 코드가 같아서 **우연히 맞았다.** 그 노선으로 확인하면 멀쩡해 보인다 — 검증은 반드시 서울·도쿄·오사카로 한다.

---

## 7. 캐시와 비용

**아낄 AI 호출이 없다.** 요청마다 링크를 새로 조립하는 비용은 0ms 이고, 캐시를 맞아도 같은 값을 다시 만든다. `search_results` 에 행이 남기는 하지만(관광지와 같은 길) 그 행이 하는 일은 없다.

비용이 드는 건 **애드픽 링크 변환** 하나뿐이다. 트립닷컴·마이리얼트립만 타고, `affiliate_links` 에 `source_url` 단위로 캐시된다.

⚠️ **주소에 날짜·인원이 들어가면서 그 캐시의 적중률이 떨어졌다.** 예전에는 모두가 같은 주소(내일·+7일·1인)를 받아 하루 한 번만 변환했는데, 지금은 발화마다 주소가 달라진다. 캐시 미스면 **요청 경로에서 애드픽을 기다린다**(타임아웃 2초) — 5초 예산에서 작지 않은 몫이다.

## 8. DB 에 남는 것

노출 한 줄은 호텔과 **같은 테이블 같은 칸**에 들어간다. 0007 이 도메인별 위성 테이블로 갈라뒀던 것을 0013 이 도로 합쳤다.

| 컬럼 | 호텔 | 항공권 |
|---|---|---|
| `recommendations.city_slug` | 도시 | **도착지** |
| `recommendation_items.item_name` | 항목명 | **`트립닷컴 ICN→KIX`** (플랫폼 + 구간) |
| `recommendation_items.price` | 1박 최저가 | **항상 null** (가격을 조사하지 않는다) |
| `recommendation_items.image_url` | 예약 페이지 썸네일 | 항상 null (카드에 이미지가 없다) |

> ⚠️ **`price` 는 두 도메인이 뜻이 다른 값을 한 칸에 넣는다.** 가르는 것은 `domain` 뿐이니 집계할 때 반드시 걸어야 한다. 0013 이 칸을 줄이면서 그 책임이 읽는 쪽으로 옮겨갔다.

> `airline` · `stops` · `cabin` · `duration_minutes` 는 0013 에서 **사라졌다.** 카드에는 여전히 찍히지만(그 값은 `search_results` 에서 온다) DB 에서 읽는 코드가 없었다.

담기는 건 "노출된 항목의 이름"이다. 나중에 로그에서 알아볼 수 있게 항공사·편명·구간을 합쳐 넣는다.

## 9. 설정

| 환경변수 | 기본값 | 무엇 |
|---|---|---|
| `FLIGHT_CACHE_TTL_MINUTES` | `360` (6h) | 저장된 행의 수명. 실제로 하는 일은 없다 (§7) |
| `FLIGHT_DEFAULT_ORIGIN_NAME` | `서울` | 출발지를 말 안 했을 때 |
| `FLIGHT_DEFAULT_ORIGIN_CODE` | `ICN` | 〃 (국내선이면 김포로 바뀐다) |
| `RESULT_MAX_ITEMS` | `20` | 줄이 플랫폼 수(3)뿐이라 걸리지 않는다 |

> `OPENAI_*` 는 항공권과 무관하다. **OPENAI_API_KEY 가 없어도 항공권은 동작한다** — 의도 파싱이 키워드로 풀리는 발화라면 모델을 아예 안 부른다.

## 11. 알려진 한계

- **가격이 카드에 없다** (2절). 플랫폼별 비교가 사라졌고, 시세표(배치)를 얹기 전까지는 그대로다
- **날짜 파서가 규칙이다.** "추석 연휴"·"벚꽃 필 때" 같은 말은 못 읽는다. 못 읽으면 기본값(내일·+7일)으로 열고 고지에 적는다
- **애드픽 캐시 적중률이 낮다** (7절). 주소에 날짜·인원이 들어가면서 질문마다 변환이 새로 나간다
- 그룹챗방에서 **콜백 푸시가 실제로 도착하는지 검증되지 않았다.** 안 되면 콜백을 끄고 "잠시 뒤 다시 물어봐 주세요" 로 통일해야 한다
- `action: "block"` 더보기 버튼이 그룹챗방에서 동작하는지도 미검증. 안 되면 `MORE_BUTTON_STYLE=message` 로 전환한다
