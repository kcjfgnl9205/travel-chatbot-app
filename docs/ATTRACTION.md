# 관광지 검색 — 발화에서 말풍선까지

> "오사카 관광지 추천해줘" 한 줄이 들어와서 `listCard` 다섯 줄이 나가기까지.
> 라우터 공통 구조는 [ROUTER.md](./ROUTER.md), 호텔·항공권은 [HOTEL.md](./HOTEL.md) · [FLIGHT.md](./FLIGHT.md).

**호텔·항공권과 결정적으로 다른 점 하나: 제휴 링크 단계가 통째로 없다.**

관광지는 우리가 파는 게 아니라 장소다. 예약 페이지가 없으니 애드픽에 변환할 주소도 없고, 그래서 rate limit 도 변환 실패 폴백도 없다. 링크는 **이름 + 도시로 우리가 만든 구글맵 주소**다.

이게 이 도메인에서 가장 큰 단순화다. 모델에게 URL 을 안 받으므로
- 허용 호스트 목록이 없고
- 링크가 죽었는지 확인할 일이 없고
- 모델이 지어낸 주소로 사용자가 404 를 보는 일도 없다

---

## 1. 어떤 발화가 관광지로 오나

### 키워드

```
관광 · 명소 · 가볼 · 볼거리 · 놀거리 · 맛집 · 구경 · 여행지
```

**호텔 → 항공권 → 관광지 순으로 본다.** 셋 다 걸리면 호텔이 이긴다.

### 판정은 3단계

| 단계 | 무엇 | 모델 호출 | 예시 |
|---|---|---|---|
| ① 대표 명령어 | `/여행지 오사카` · `관광지 오사카` · `맛집 오사카` | **0회** | |
| ② 키워드 + 도시 사전 | 관광 키워드 + 237개 도시표 | **0회** | "오사카 관광지 추천해줘" |
| ③ 모델 | 위 둘로 안 되면 gpt-5-mini | 1회 | "도톤보리 근처 볼거리" |

대표 명령어는 `여행지` · `관광지` · `맛집` 셋 다 관광지로 매핑된다.

### 발화별 파싱 결과

| 발화 | place | 경로 |
|---|---|---|
| `오사카 관광지 추천해줘` | 오사카 | ② |
| `오사카 가볼 만한 곳` | 오사카 | ② |
| `여행지 도톤보리` | 도톤보리 | ① |
| `오사카 맛집 알려줘` | 오사카 | ② |
| `베트남 여행지` | 베트남 | ② → **도시 되묻기** |

### ⚠️ 맛집도 여기로 온다

`맛집` 키워드는 관광지로 매핑되지만, **검색 프롬프트는 "맛집"을 따로 다루지 않는다.** 일반 관광지를 찾고 그중 `음식/시장` 카테고리가 섞여 나올 뿐이다. 맛집만 원하는 사용자에게는 기대와 다른 결과다 — 알려진 한계(10절).

### ⚠️ 테마는 아직 파싱하지 않는다

"아이랑 갈 만한", "야경 좋은" 같은 조건은 뽑지도, 고지하지도 않는다. 날짜·인원처럼 `ignored` 에 담기지도 않아서 **사용자는 반영된 줄 안다.** 이것도 한계다.

## 2. 발화 → 응답 전체 흐름

```
"@여행메이트 오사카 관광지 추천해줘"
  │
  │  ── 카카오 5초 예산 안 ─────────────────────────────
  │
  ├─ 의도·지명 추출            → intent=attraction, place=오사카
  ├─ 지역 정규화               "오사카" → place_id=42
  ├─ 캐시 조회                 attraction:42
  │    ├ 히트 → listCard 즉시 ✅
  │    └ 미스 → pending 선점 → 아래로
  │
  │  ── 백그라운드 ────────────────────────────────────
  │
  ├─ 구글 Places 검색          타입별 6회 → 후보 ~50곳    ← 존재가 보장된다
  ├─ 모델이 순서 재정렬        1회 (웹 검색 없음)         ← 한국인 여행자 관점
  ├─ 지도 링크 생성            place_id → 정확한 핀
  ├─ 중복 제거                 place_id 기준
  ├─ 사진 확보                 위키미디어 ko → en → commons
  ├─ attraction_places 에 place_id 저장 (영구)
  ├─ search_results 에 20건 저장 (TTL 30일)
  └─ 카드 조립 → callbackUrl 로 POST
```

> **미리 채워둔 도시는 이 아래가 통째로 없다.** 배치가 하루 한 번 돌면서 자주 묻는
> 도시를 데워두므로, 그 도시들은 **첫 질문부터 카드가 즉시** 나간다 (9절 참고).

## 3. 상황별로 무엇이 나가나

호텔·항공권과 같다. 주어만 `오사카 관광지` 로 바뀐다.

| 상황 | 실제 문구 |
|---|---|
| 미스 + 콜백 켜짐 | `오사카 관광지를 찾고 있어요. 잠시만요 🔍` |
| 미스 + 콜백 꺼짐 | `오사카 관광지를 찾고 있어요 🔍`<br>`30초쯤 뒤에 다시 물어봐 주세요!` |
| 남이 검색 중 | `오사카 관광지를 먼저 찾고 있어요 🔍` |
| 결과 0건 | `오사카 관광지 정보를 지금은 정리하지 못했어요 🙏` |
| 검색 실패 | `오사카 관광지를 불러오지 못했어요 🙏` |
| 키가 없어 불가 | `지금은 오사카 관광지 검색이 안 되고 있어요 🙏` |
| 나라를 말함 | `베트남 어느 도시의 관광지를 찾을까요?` |

> `관광지` 는 받침이 없어 조사가 `를` 다. 문구를 `${...}을` 로 박아두면 **"관광지을 찾으세요?"** 가 나간다 — 실제로 나갔다. [`withObjectParticle()`](../src/modules/kakao/cards.ts) 이 음절 코드로 받침을 판정한다.

```json
{
  "version": "2.0",
  "template": {
    "outputs": [
      { "listCard": {
          "header": { "title": "오사카 관광지 5곳" },
          "items": [
            { "title": "오사카성",
              "description": "★ 4.4 (61,234) · 역사/문화 · 주오구",
              "imageUrl": "https://upload.wikimedia.org/....jpg",
              "link": { "web": "https://bot.nolmoa.com/r/Rt4nP8wLc1Yj" } }
          ],
          "buttons": [
            { "label": "더 보기", "action": "block", "blockId": "...",
              "messageText": "오사카 관광지 더 보기",
              "extra": { "cache_key": "attraction:42", "offset": 5 } }
          ] } }
    ],
    "quickReplies": [
      { "label": "도쿄 관광지", "action": "message", "messageText": "도쿄 관광지 추천해줘" },
      { "label": "후쿠오카 관광지", "action": "message", "messageText": "후쿠오카 관광지 추천해줘" }
    ]
  }
}
```

**고지 말풍선이 대개 없다.** 관광지는 날짜·인원을 쓰지 않으므로 버릴 조건도 없다. 사용자가 "9월에 오사카 관광지" 라고 하면 그때만 고지가 붙는다.

### 머리글

| 페이지 | 문구 |
|---|---|
| 1페이지 | `오사카 관광지 5곳` |
| 2페이지부터 | `오사카 관광지 6~10번째` |

### 한 줄의 제목·설명

```
title        관광지 이름                  (40자, 2줄) — 구글 지도에 뜨는 그 표기
description  평점 · 카테고리 · 위치        (40자, 1줄)
imageUrl     위키미디어 사진 (없을 수 있다)
link.web     /r/{clickId} → 302 → 구글맵 (place_id 로 정확한 핀)
```

[`listDescription()`](../src/modules/attraction/attraction-card.ts) 의 우선순위는 **평점 → 카테고리 → 위치**다.

> **리뷰 수를 평점과 같이 보여준다.** 평점 4.8 에 리뷰 3개는 4.3 에 리뷰 5만 개보다 못 믿는데, 별점만 찍으면 그 차이가 지워진다.

### 평점 표기

| 상황 | 표기 |
|---|---|
| 평점 + 리뷰수 | `★ 4.4 (61,234)` |
| 리뷰 수를 모름 | `★ 4.4` |
| 평점 없음 | 생략 (리뷰가 없는 장소가 있다) |

## 5. ⚠️ 입장료·소요시간을 모으지 않는다

**구글이 입장료를 주지 않고, 모델은 지어낸다.** 그래서 아예 안 모으기로 했다.

예전에는 모델에게 웹 검색을 시켜 받았는데, 원화 환산을 시켰더니 **1,200엔짜리 오사카성이 `5,760원`, 2,700엔짜리 카이유칸이 `2,700원`** 으로 나왔다. 환율을 모른 채 현지 통화 숫자를 원화 칸에 넣거나 엉뚱하게 곱한 결과다.

통화를 함께 받는 것으로 한동안 버텼지만, 목록의 출처를 구글로 옮기면서 **"모델에게 사실을 묻지 않는다"** 를 규칙으로 세웠다. 입장료는 그 규칙의 예외로 둘 만큼 중요하지 않다 — 대신 들어온 평점이 고를 때 더 쓸모 있고, 지도로 넘어가면 같은 숫자가 다시 보여 앞뒤가 맞는다.

> **틀린 가격은 없는 가격보다 나쁘다.** 2,700원인 줄 알고 갔다가 27,000원을 낸다.

입장료가 필요해지면 환율 API 를 붙이고 **공식 홈페이지를 긁는** 별개의 작업이 된다. 모델에게 다시 묻는 것은 답이 아니다.

## 6. 링크를 우리가 만든다

```ts
mapUrl = mapsUrl(관광지명, 도시명)
// https://www.google.com/maps/search/?api=1&query=오사카성%20오사카
```

모델에게 URL 을 묻지 않는다. 호텔에서 확인했듯 모델은 그럴듯한 주소를 지어내고, 그건 카드에 깨진 자리만 남긴다.

**도시명을 붙이는 이유** — "시청" 같은 이름은 전 세계에 있다. 도시를 붙이면 구글맵이 그 도시 안에서 찾는다.

### 그래도 `/r/{clickId}` 를 거친다

수수료가 없는데도 리다이렉트를 한 홉 끼운다. **어떤 관광지를 눌렀는지는 알아야 다음 추천이 나아지기** 때문이다. 카카오 링크는 브라우저를 바로 열어서, 한 홉이 없으면 아무 신호도 오지 않는다.

그래서 코드상 차이는 이렇다:

| | 호텔·항공권 | 관광지 |
|---|---|---|
| 애드픽 변환 | ✅ | ❌ |
| `affiliate_link_id` | 있음 | `null` |
| subid 파라미터 | 붙임 | **안 붙임** |
| 변환 실패 경고 | 있음 | 없음 |
| `/r/{clickId}` | ✅ | ✅ |

공유 렌더러([`RecommendationRowsService`](../src/modules/recommendation/rows.service.ts))는 `links` 를 **안 받으면** "변환을 다루지 않는 도메인"으로 알아서 처리한다. 빈 `Map` 과는 뜻이 다르다 — 빈 Map 은 "변환을 시도했는데 못 건졌다"라 경고 대상이다.

> `AttractionModule` 이 `AffiliateModule` 을 import 하지 않는다. 이 차이가 모듈 그래프에 그대로 보이는 게 맞다.

## 7. 사진 — 위키미디어에서 찾는다

```
① 한국어판 검색   이름 + 도시명
② 영어판 검색     nameEn + 도시 슬러그      ← 한국어 문서가 없을 때
③ 커먼즈 검색     nameEn                    ← 문서가 아예 없을 때
④ 못 찾으면 null  그 줄만 사진 없이 나간다
```

호텔은 예약 페이지에서 og:image 를 긁었지만, 관광지는 **긁어올 페이지 자체가 없다.** 위키미디어 API 는 구조화된 이미지 주소를 주므로 지어낼 자리가 없다 — 지도 링크를 우리가 만드는 것과 같은 이유다.

### ⚠️ 구글 Places 사진을 쓰지 않는다

목록과 평점은 구글에서 받으면서 사진만 위키미디어인 게 이상해 보이지만, 이유가 분명하다.

| | 위키미디어 | 구글 Places |
|---|---|---|
| 커버리지 | 87%+ | 거의 100% |
| **이미지 주소 수명** | **영구** | **만료** |
| 비용 | 0 | 호출마다 과금 (별도 SKU) |

**카카오 카드는 단톡방에 영구히 남는다.** 사람들이 일주일 뒤 스크롤해서 다시 보는데, 그때 주소가 만료돼 있으면 사진 자리가 깨진 채로 남는다. 우회로(렌더링 때마다 재조회 · 프록시 · 내려받기)는 각각 5초 예산·본 사람 수만큼의 호출·약관에 걸린다.

**구글이 이기는 건 커버리지 한 칸뿐이고, 그건 커먼즈 폴백으로 상당 부분 따라잡는다.**

### 영문명을 따로 받는 이유

실측 커버리지 (도시 8곳 × 5곳 = 40곳):

| 언어 | 커버리지 | 비고 |
|---|---|---|
| ko 만 | 62% | 일본·유럽 100%, 동남아 0~40% |
| ko → en | **87%** | 한국어 문서가 없는 동남아를 영문명이 메운다 |
| ko → en → commons | 측정 예정 | 문서가 아예 없는 작은 장소를 커먼즈가 줍는다 |

그래서 `name_en` 을 모델에게 따로 받는다. 카드에는 안 쓰이고 **위키미디어 검색어로만** 쓴다 — 이건 사실 조회가 아니라 **표기 변환**이라 모델이 잘하는 일이다(구글은 `languageCode: ko` 로 물어서 한국어 이름을 준다). 모르면 지어내지 말고 `null` 로 두라고 시킨다.

어느 언어판에서 건졌는지는 로그에 남는다 — `image ko attraction=오사카성 doc=...`. ko/en 비율이 영문명의 값어치를 보여준다.

> 위키미디어는 봇에 연락처가 담긴 User-Agent 를 요구한다. 익명 UA 로 두들기면 차단된다.

> ⚠️ **저작권.** 위키미디어 사진은 대부분 CC BY-SA 라 엄밀히는 저작자 표시가 필요하다. `listCard` 한 줄에는 링크가 하나뿐이고 그 자리는 지도가 써야 해서(클릭 추적) 줄마다 출처를 달 자리가 없다.

## 8. 결과는 어떻게 만들어지나

[`GooglePlacesAttractionProvider`](../src/modules/attraction/providers/places.provider.ts).

```
1차  구글 Places       타입별 6회 → 후보 ~50곳    존재가 보장된다
2차  모델              그중 20곳을 순서대로       한국인 여행자 관점
3차  모델              영문명 (사진 검색용)       표기 변환
4차  위키미디어        사진 (동시에)
```

**호텔·항공권의 2단 웹 검색 구조를 쓰지 않는다.** 그쪽은 "웹에 뭐가 있나" 부터 모델이 찾아야 하지만, 관광지는 **구글이 정답 목록을 갖고 있다.** 모델에게 검색까지 시키면 없는 곳을 섞고 주소·가격을 지어낸다 — 그게 이 도메인에서 실제로 문제였다.

### 역할이 갈린다

| | 하는 일 | 안 하는 일 |
|---|---|---|
| **구글** | 어떤 곳이 있나 · 이름 · 평점 · 위치 · 신원 | 한국인에게 뭘 먼저 보여줄까 |
| **모델** | **순서만** · 사진 검색용 영문명 | 사실은 하나도 안 채운다 |

모델이 돌려주는 건 **place_id 배열 하나**다. 새 항목을 만들 자리도, 값을 고칠 자리도 스키마에 없다. 후보에 없는 id 는 버리고, 모델이 빠뜨린 후보는 뒤에 붙인다 — **모델이 헛돌아도 목록은 살아 있고 순서만 구글 기본값이 된다.**

### ⚠️ 왜 모델에게 순서를 맡기나

구글 순서는 인기·거리 기준이라 **한국인 여행자 관점이 아니다.** 현지인 기준 장소가 섞이고, 한국인에게만 유명한 곳이 빠진다. 그리고 평점만으로 줄 세우면 리뷰 3개짜리 카페가 1등이 된다.

그래서 프롬프트가 시키는 건 셋이다 — 카테고리를 섞어라 · 평점이 높아도 리뷰가 적으면 뒤로 · 현지 편의시설은 뒤로.

### 카테고리는 구글 타입에서 온다

```
관광명소 · 역사/문화 · 미술관/박물관 · 자연/공원 · 거리/쇼핑 · 테마파크
```

한 번에 "오사카 관광지" 로 부르면 비슷한 성격이 스무 곳 나온다. **타입을 갈라 부르는 것이 곧 카테고리 다양성이다** — 모델에게 "반드시 섞어라" 라고 사정할 필요가 줄어든다. 같은 장소가 여러 타입에 걸리면 먼저 걸린 쪽의 카테고리를 쓴다.

### 이름·위치를 다듬는 코드가 사라졌다

예전에는 모델이 `오사카 과학관/가족 체험 공간` 같은 이름을 줘서 `placeName()` 이 슬래시 뒤를 잘라내야 했고, 위치에 도시 이름이 붙어 와서 떼어내야 했다. **구글은 그런 걸 주지 않는다** — `displayName` 은 지도에 뜨는 그 표기이고, 위치는 주소 구성요소에서 `sublocality` 를 골라 쓴다.

### 중복 제거 — `place_id` 기준

이름으로 판정하면 `오사카성` / `오사카 성` / `Osaka Castle` 이 전부 다른 값이 된다. **`place_id` 는 표기와 무관하게 같다.** 예전에는 `mapUrl`(이름으로 만든 값)로 흡수하려 했는데, 이제 신원이 진짜로 생겼다.

## 9. 캐시 · DB · 설정

### TTL 이 가장 길다 — 30일

| 도메인 | TTL | 근거 |
|---|---|---|
| 항공권 | 6시간 | 운임이 제일 빨리 변한다 |
| 호텔 | 24시간 | |
| **관광지** | **30일** | 오사카성은 없어지지 않는다 |

캐시 키는 `attraction:{place_id}`.

### 저장이 두 층으로 갈린다 ← **이 도메인의 핵심**

구글 약관은 `place_id` 외의 콘텐츠를 오래 보관하는 걸 제한한다. 그래서 수명이 다른 두 곳에 나눠 담는다.

| 저장소 | 무엇 | 수명 |
|---|---|---|
| **`attraction_places`** | 도시별 **`place_id` + 추천 순서** | **영구** |
| `search_results` | 이름 · 평점 · 사진 · 위치 · 주소 | **30일** |
| `recommendation_items` + `_attractions` | 누가 뭘 보고 눌렀나 | 영구 |

**캐시가 비어도 모델을 다시 부르지 않는다.** 순서가 `attraction_places` 에 남아 있으므로 구글에 `place_id` 로 다시 물어 살만 채우면 된다.

> `attraction_places` 는 **배치만 쓰는 게 아니다.** 사용자가 물어서 찾은 도시도 같이 저장한다([`AttractionService.search()`](../src/modules/attraction/attraction.service.ts)) — 배치 경로에만 두면 온디맨드로 찾은 도시는 30일 뒤 목록을 처음부터 다시 만들어야 한다.

> ⚠️ **관광지만 "만료돼도 보여주기" 를 쓰지 않는다.** 다른 도메인은 만료된 값이라도 보여주고 뒤에서 갱신하는데([0004](../supabase/migrations/0004_router.sql)), 관광지 행에는 구글 콘텐츠가 들어 있어 30일이 지나면 쓰면 안 된다. 배치가 돌 때 실제로 지운다.

### 노출 스냅샷에 남는 것

| 컬럼 | 값 |
|---|---|
| `recommendation_items.item_name` | 관광지 이름 |
| `recommendation_items.source_url` · `target_url` | `mapUrl` (변환 없음) |
| `recommendation_item_attractions.place_id` | **구글 신원.** 관광지 단위 집계는 이 칸으로 |
| `..._attractions.category` · `area` · `image_url` | 카테고리 · 위치 · 사진 |

> ⚠️ **평점·리뷰수·주소는 스냅샷에 없다.** 구글 콘텐츠라 영구 보관하지 않는다 — "그때 평점이 몇이었나" 는 30일 캐시가 살아 있는 동안만 알 수 있다.

> ⚠️ **판매처·제휴 링크 칸도 없다.** 관광지는 우리가 파는 게 아니라 장소라서 변환할 주소가 없다 — 칸이 없는 것이 곧 이 도메인의 정체다.

> ⚠️ **수익 집계에서 관광지를 빼야 한다.** `domain='attraction'` 행은 클릭이 있어도 수수료가 0이다.

### 배치 — 미리 채워두기

```
크론 (하루 1회)
  └─ POST /api/v1/catalog/refresh   ← **바로 돌아온다**
       마지막 갱신이 28일 지난 도시 4곳
       → [백그라운드] 구글 재검색 → 모델 재정렬 → 캐시 채움 → 갱신 도장
       → 만료된 관광지 캐시 삭제
```

> ⚠️ **응답을 기다리지 않는다.** 도시 하나에 30초~2분이 걸려서 기다리면 프록시 타임아웃(100초)에 걸린다 — 실제로 504 가 났다. 응답은 "무엇을 시작했는지" 이고 진행은 로그로 본다. 씨앗 등록도 같은 이유로 여러 도시를 나눠 돌린다.

미리 채워둔 도시는 **첫 질문부터 카드가 즉시** 나간다 — 지금은 "찾고 있어요" 후 콜백을 기다려야 한다.

> ⚠️ **갱신 주기는 캐시 TTL 보다 짧아야 한다** (28일 < 30일). 만료된 뒤에 갱신하면 그 도시의 첫 질문이 다시 대기를 타므로 미리 채워두는 의미가 없다.

> ⚠️ **스케줄러는 앱에 없다.** 서버가 여러 대여도 배치는 하나만 돌아야 하는데, 그 조율은 운영이 한다. 앱에 타이머를 넣으면 인스턴스 수만큼 같은 도시를 찾고 그게 그대로 API 요금이다.

씨앗 도시는 **아시아(일본·한국·동남아·중화권) 112곳** — `POST /api/v1/catalog/seed` 로 한 번만 등록한다. 나머지 도시가 막히는 건 아니다. 누가 물으면 그 자리에서 찾고, 그때부터 배치 대상이 된다.

### 설정

| 환경변수 | 기본값 | 무엇 |
|---|---|---|
| `GOOGLE_PLACES_API_KEY` | — | **비어 있으면 관광지 검색이 안 된다** |
| `GOOGLE_PLACES_TIMEOUT_SECONDS` | `5` | 도시 하나에 6회 부른다 |
| `ATTRACTION_REFRESH_DAYS` | `28` | 배치 주기. TTL 보다 짧아야 한다 |
| `ATTRACTION_CACHE_TTL_MINUTES` | `43200` (30일) | 검색 결과 수명 |
| `ATTRACTION_IMAGES` | `true` | 끄면 사진 단계를 통째로 건너뛴다 |
| `ATTRACTION_IMAGE_TIMEOUT_SECONDS` | `3` | 위키미디어 호출 제한 |
| `RESULT_MAX_ITEMS` | `20` | 4페이지 |

## 11. 알려진 한계

- **맛집을 따로 다루지 않는다** (1절). `맛집` 발화는 일반 관광지 검색으로 가고 `음식/시장` 카테고리가 섞여 나올 뿐이다
- **테마를 파싱하지 않는다** — "아이랑", "야경" 은 뽑지도 고지하지도 않아서 사용자는 반영된 줄 안다
- **사진이 13% 정도 빈다.** 사진 없는 줄이 섞이는 건 정상이다
- **사진 출처를 줄마다 표시하지 못한다** (7절)
- 영업시간·휴무일을 다루지 않는다. 폐관한 곳을 거르는 건 프롬프트 지시뿐이다
