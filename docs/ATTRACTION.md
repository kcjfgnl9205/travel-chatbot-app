# 관광지 추천 — 어떻게 도는가

"오사카 관광지 추천해줘" 한 줄이 `listCard` 다섯 줄이 되기까지.

정의 원본은 코드다. 이 문서는 **왜 그렇게 생겼는지**와 **손댈 때 뭘 깨뜨릴 수 있는지**를 설명한다.

> **전제**: 관광지는 우리가 파는 게 아니라 **장소**다. 예약도, 제휴 수수료도 없다.
> 그래서 이 도메인은 호텔·항공권에서 가장 복잡했던 부분(애드픽 변환, 허용 호스트,
> 죽은 링크 처리)이 통째로 빠진다. 대신 링크는 우리가 직접 만든다.

호텔은 [README](../README.md#호텔은-어떻게-찾는가), 항공권은 [FLIGHT.md](FLIGHT.md), DB 는 [DB.md](DB.md).

## 1. 한눈에

```
"오사카 관광지 추천해줘"
   │
   ├─ ① 발화 파싱  NluService  ← **호텔과 같은 파서다** (뽑을 게 도시 하나로 같다)
   │     → { osaka, 오사카 }                         (~2초, 5초 예산 안)
   │
   ├─ ② 사용자/메시지 로깅            users · messages (domain='attraction')
   │
   ├─ ③ 캐시 조회  SearchCacheService  메모리 → Supabase   (수십 ms)
   │     ├─ 히트 → ⑤ 로 바로 간다
   │     └─ 미스 → 여기서 응답을 만들 수 없다 (검색이 7~30초)
   │              ↓
   │        useCallback 응답 반환 ────────────────┐
   │              ↓ (백그라운드)                  │
   ├─ ④ 검색  OpenAiAttractionProvider            │
   │     1차: web_search 로 후보 15곳 수집         │
   │     2차: 카테고리를 섞어 5곳 선정              │
   │     → 정규화 (이름 정리 / 통화 검증 / 지도 URL 생성)
   │     → search_cache 저장 (24시간)             │
   │              ↓                               │
   ├─ ⑤ 카드 조립  listCard 5줄                    │
   │     곳마다 clickId 발급 → recommendation_items │
   │              ↓                               │
   └─ ⑥ callbackUrl 로 POST ──────────────────────┘  (카카오 1분 예산)

[줄 클릭] → /r/{clickId} → click_count +1 → 302 → 구글맵
```

**애드픽 단계가 없다.** 호텔·항공권 흐름과 비교하면 그 한 칸이 빠진 것이 전부다.

진입점: [`attraction.service.ts`](../src/modules/attraction/attraction.service.ts) `handle()`

## 2. 링크를 우리가 만든다 — 이 도메인의 핵심

[`common/maps-url.ts`](../src/common/maps-url.ts)

```ts
mapsUrl('오사카성', '오사카')
// https://www.google.com/maps/search/?api=1&query=오사카성%20오사카
```

호텔·항공권에서는 **모델이 준 URL** 을 써야 했다. 모델은 없는 주소를 그럴듯하게 지어내므로 허용 호스트 목록([booking-url.ts](../src/common/booking-url.ts))으로 걸러야 했고, 그래도 통과한 게 404 이면 사용자가 그걸 본다.

지도는 그럴 이유가 없다. 구글이 공개한 [URL 규약](https://developers.google.com/maps/documentation/urls/get-started#search-action)에 이름만 끼워 넣으면 되므로 **지어낼 자리가 없다.** 결과적으로 이 도메인에는

- 허용 호스트 목록이 없다
- 링크가 살아 있는지 확인할 일이 없다
- `droppedUntrusted` 같은 탈락 사유가 없다 (이름이 없어서 버리는 것뿐)

### ⚠️ 좌표는 쓰지 않는다

스키마에 `lat`/`lng` 를 넣으면 모델이 채워주긴 한다. 그런데 **LLM 의 좌표는 그럴듯하고 자주 틀린다.** 엉뚱한 곳에 핀이 꽂히는 건 이름으로 검색되는 것보다 나쁘다 — 사용자는 지도가 틀렸다는 걸 현장에서야 안다.

이름 검색은 구글이 알아서 맞춰주고, 장소 카드(사진·영업시간·리뷰)까지 뜬다.

### 도시명을 붙이는 이유

"중앙공원", "시립미술관" 같은 이름은 전 세계에 널려 있다. 사용자가 물어본 도시를 같이 넣어야 엉뚱한 나라로 가지 않는다.

### 그래도 `/r/{clickId}` 를 거친다

수수료가 없는데 리다이렉트를 끼우는 이유는 하나다 — **어떤 관광지를 눌렀는지 알아야 하기 때문이다.** 카카오 링크는 브라우저를 바로 열어서, 구글맵 주소를 카드에 직접 박으면 우리 서버로 아무 신호도 오지 않는다. 호텔에서 리다이렉트를 끼운 것과 같은 이유이고, 같은 코드다.

부수 효과로 `source_url == target_url` 이 된다 (중간에 변환이 없으므로). 호텔·항공권에서 이 둘이 다른 것과 대비된다.

## 3. 발화 파싱 — 호텔 파서를 그대로 쓴다

관광지가 뽑아야 하는 건 **도시 하나**뿐이다. 호텔과 똑같다. 그래서 [`NluService`](../src/modules/nlu/nlu.service.ts) 를 그대로 쓴다.

공짜로 따라오는 이득이 있다: **별칭 캐시가 공유된다.** "오사카 호텔 추천해줘" 를 물어본 사람이 "오사카 관광지 추천해줘" 를 물으면 파싱이 캐시에서 나간다.

| 도메인 | 파서 | 이유 |
|---|---|---|
| 호텔 | `NluService` | 도시 + 인원 |
| **관광지** | **`NluService`** (공유, `cityOnly`) | 도시 하나 — 호텔과 같다 |
| 항공권 | `FlightNluService` | 노선 2개 + 날짜 + 편도/왕복 → 스키마가 다르다 |

호텔과 다른 점이 하나 있다. 관광지는 `cityOnly: true` 로 부른다 — 인원·박수를
알아도 쓸 데가 없으므로, 도시가 정해진 뒤에 그걸 뽑자고 모델을 한 번 더 부르지
않는다 ("세부 관광지 5곳 추천해줘" 의 "5" 때문에 2.5초를 쓸 이유가 없다).

### 테마("아이랑", "야경")는 아직 파싱하지 않는다

지금은 도시만 본다. 테마를 넣으려면 **캐시 키에 테마가 같이 들어가야 한다** — 안 그러면 "오사카 관광지" 와 "오사카 아이랑 갈만한 곳" 이 같은 캐시 칸을 쓰고, 두 번째 사람이 첫 번째 사람의 결과를 받는다. 발화 원문을 검색 프롬프트에 그대로 넘기는 방법도 있지만 같은 캐시 문제가 생긴다.

## 4. 검색 — gpt-5-mini 2단 호출

[`providers/openai.provider.ts`](../src/modules/attraction/providers/openai.provider.ts)

| | 1차 (findCandidates) | 2차 (rank) |
|---|---|---|
| 목적 | 후보 15곳 수집 (`OPENAI_CANDIDATE_COUNT`) | 5곳 선정 (`ATTRACTION_RESULT_LIMIT`) |
| 툴 | `web_search` | 없음 |
| 스키마 | `attraction_candidates` | `attraction_picks` |

2차가 하는 일이 호텔·항공권보다 하나 더 있다 — **카테고리를 섞는 것.** 그냥 두면 신사 다섯 곳, 전망대 다섯 곳이 나온다. 그래서 카테고리를 enum 으로 고정하고(`CATEGORIES`) 프롬프트에서 명시적으로 섞으라고 시킨다. `trace.counts.categories` 로 쏠렸는지 확인할 수 있다.

### ⚠️ 1차 스키마에 없는 필드는 2차가 절대 못 채운다

**이 저장소에서 두 번 겪은 버그다.** 호텔 썸네일이 항상 `null` 이던 것도 같은 원인이었다 (1차 후보 스키마에 이미지 필드가 없는데 2차는 "후보에 적히지 않은 건 null" 규칙을 지켰다 — 구조상 절대 채워지지 않았다).

관광지에서는 `duration_minutes` 가 똑같이 당했다. 2차 스키마에만 넣고 "추정해도 된다" 고 적었는데 실측하니 **5곳 전부 null** 이었다. 1차 후보 스키마에 필드를 추가하고 나서야 채워졌다.

> **새 필드를 넣을 때는 1차·2차 스키마를 같이 본다.** 한쪽만 고치면 조용히 안 채워진다.

### ⚠️ 입장료를 원화로 환산시키지 않는다

처음에는 "원화로 환산해서 적어라" 로 시켰다. 실측 결과:

| 관광지 | 실제 | 모델이 준 값 |
|---|---|---|
| 오사카성 | 1,200엔 (≈12,000원) | **"약 5,760원"** |
| 카이유칸 | 2,700엔 (≈27,000원) | **"약 2,700원"** ← 엔화 숫자를 원화 칸에 그대로 |
| 우메다 공중정원 | 1,500엔 (≈15,000원) | **"약 1,000원"** |

**모델은 환율 계산을 못한다.** 검색 결과에 적힌 숫자를 옮기는 건 잘한다. 그래서 지금은 **현지 통화 그대로** 받고 통화 코드(`JPY`, `THB` …)를 함께 받아 `1,200엔`, `500바트` 로 표기한다.

2,700원인 줄 알고 갔다가 27,000원을 내는 건 **가격을 안 보여주는 것보다 나쁘다.**

부수 규칙 두 개:

- **통화를 모르면 금액도 버린다.** `1,200` 만 보여주면 한국인은 원으로 읽는다 — 정확히 우리가 막으려는 오해다. 대신 `유료` 라고만 쓴다.
- 아는 통화가 아니면 코드를 그대로 붙인다 (`25 MYR`). 읽기 조금 불편해도 **맞는 숫자**가 낫다.

### ⚠️ 이름은 두 가지를 동시에 만족해야 한다

이름은 **카드 제목**이자 **구글맵 검색어**다. 한쪽만 시키면 다른 쪽이 무너진다 — 둘 다 실측으로 겪었다.

| 시킨 것 | 나온 것 | 문제 |
|---|---|---|
| "한국인이 검색할 표기" | `오사카 과학관/가족 체험 공간` | 이 검색어로는 지도에 아무것도 안 나온다 |
| "그 장소의 공식 명칭만" | `Umeda Sky Building Kuchu Teien Observatory` | 영문 + 40자 초과로 카드에서 잘림 |

지금은 **한국어 표기 + 장소 이름만 + 20자 이내**를 다 명시하고, 코드에서 한 번 더 정리한다(`placeName()`): 슬래시 뒤를 버리고, 끝의 괄호 설명을 떼어낸다.

```
'오사카 난바 파크스/Namba Parks 쇼핑 & 레저' → '오사카 난바 파크스'
'유니버설 스튜디오 재팬(USJ)'                 → '유니버설 스튜디오 재팬'
```

잘라낸 게 전부면 원문을 쓴다 — 이름이 없는 것보단 낫다.

### 위치(area)

가장 가까운 역·번화가를 짧게 받는다. 도시 이름이 앞에 붙어 오면(`오사카시 스미노에구`) 떼어내고, 도시 이름뿐이면(`오사카`) 버린다 — 사용자는 이미 그 도시를 물어봤다.

슬래시 병기도 앞 조각만 남긴다 (실측: 방콕에서 `앙깡/시내` 가 나왔다).

## 5. 캐시 — TTL 이 가장 길다

| 도메인 | TTL | 이유 |
|---|---|---|
| 호텔 | 60분 | 객실 요금이 바뀐다 |
| 항공권 | 30분 | 운임이 하루에도 몇 번 바뀐다 |
| **관광지** | **1440분 (24시간)** | **오사카의 볼거리는 어제와 오늘이 같다** |

짧게 잡을수록 같은 답을 다시 사는 셈이다. 입장료·휴관 정보가 바뀌는 주기를 생각하면 하루가 적당하다.

캐시 키는 **도시와 개수뿐**이다 (`attractionCacheKey`). 항공권처럼 날짜·인원으로 갈릴 일이 없다.

나머지 안전장치(`inFlight` 병합, `recentlyEmpty` 10분)는 호텔과 같다.

## 6. 카드 — `listCard`

항공권과 달리 **listCard 로 돌아온다.** 이유:

- 관광지 추천은 **비교**가 목적이다. 5곳이 한 화면에 세로로 나열되는 게 맞다
- 항목당 링크가 **하나**뿐이다 (지도). 항공권처럼 버튼이 둘로 갈리지 않는다
- 줄 전체가 클릭 영역이라 별도 버튼 없이 추적된다

```
오사카 관광지 5곳
  오사카성            | 1,200엔 · 2시간 · 난바
  도톤보리            | 무료 · 1시간 30분 · 난바
  쿠로몬시장           | 무료 · 1시간 · 난바
  우메다 스카이 빌딩     | 1,500엔 · 1시간 30분 · 우메다
  카이유칸            | 2,400엔 · 1시간 30분 · 미나토구
  [더 보기] [사진 출처: 위키미디어]
```

⚠️ 버튼은 둘이 한계다. '더 보기' 는 **다음 5곳이 남아 있을 때만** 달리고, '사진 출처' 는
사진이 한 장이라도 실렸을 때만 달린다. 둘 다 아니면 buttons 키가 아예 없다.
예전 '다른 도시 보기' 는 뺐다 — 누르면 도시 없는 문장이 가서 되묻기만 나왔고,
도시 전환은 quickReplies 가 이미 하고 있다.

### 40자 한 줄에 무엇을 넣을 것인가

`listDescription()` 은 **입장료 → 소요 시간 → 위치** 순으로 세 조각만 넣는다.

한 줄 소개(`description`)를 카드에 넣지 않는 이유: 소개는 40자에서 잘려 문장이 끊기는데, 그러면 세 조각 다 못 보여주고 **잘린 문장만** 남는다. 소개는 진단·캐시에만 남긴다.

빈 필드는 조용히 빠진다. 전부 비면 `description` 키 자체가 안 들어간다.

### 카드 이미지 — 위키백과에서 찾는다

호텔은 예약 페이지에서 `og:image` 를 긁어온다([thumbnail.ts](../src/modules/hotel/thumbnail.ts)). **관광지는 긁어올 페이지 자체가 없다.** 모델에게 이미지 주소를 시키는 것도 안 된다 — 호텔에서 확인했듯 없는 CDN 주소를 지어낸다.

[`attraction-image.ts`](../src/modules/attraction/attraction-image.ts) 가 위키백과 API 에서 받아온다. **구조화된 API 라 지어낼 자리가 없다** — 지도 링크를 우리가 만드는 것과 같은 이유로 이 도메인에 맞는다. 키가 필요 없고 무료다.

검색은 `generator=search` 로 한다. 정확한 문서 제목을 모르기 때문이다 — 제목으로 바로 찍는 REST summary 엔드포인트는 표기가 조금만 달라도 404 다. 도시 이름을 검색어에 붙이는 이유는 지도 링크와 같다 ("중앙공원" 은 전 세계에 있다).

#### ko → en 순서로 보고, 영문명을 모델에게 받는다

한국어 문서만 보면 **동남아가 통째로 빈다.** 실측(도시 8곳 × 5곳 = 40곳):

| 언어 | 커버리지 | 갈리는 곳 |
|---|---|---|
| ko 만 | 62% | 오사카·도쿄·파리 5/5, **세부 0/5 · 다낭 1/5 · 방콕 2/5** |
| ko → en | **87%** | 세부가 영문명으로 4/5 회수됨 |

그래서 `name_en` 을 모델에게 받는다. 카드에는 안 쓰고 영어판 검색어로만 쓴다.

⚠️ **`name_en` 은 1차·2차 스키마에 모두 넣었다.** 1차 후보 스키마에 없으면 2차는 "후보에 적히지 않은 건 null" 규칙 때문에 **구조상 절대 못 채운다** — `duration_minutes` 와 호텔 썸네일이 정확히 이것 때문에 항상 null 이었다 (4절).

#### ⚠️ 엉뚱한 사진은 사진이 없는 것보다 나쁘다

사용자는 카드에 실린 사진을 그 장소라고 믿는다. 그래서 두 규칙을 건다.

| 규칙 | 막는 것 (전부 실제로 받아본 것) |
|---|---|
| 문서 제목이 관광지 이름과 **포함 관계**여야 한다 | "유니버설 스튜디오 재팬" → **싱가포르** 사진. 글자 겹침 같은 느슨한 규칙을 쓰면 통과한다 |
| 도시 문서 자체는 거른다 | 검색이 관광지를 못 찾으면 도시 문서로 떨어지고, 그 대표 이미지는 **위치 지도**다 ("마젤란 십자가" → `Ph_locator_cebu_cebu.png`) |
| 지도·문장·로고·SVG 주소를 거른다 | 위 지도 PNG, 국기, 위키 로고 |

애매하면 포기하는 쪽으로 기울였다. 그래서 "시부야 스크램블 교차로"(문서명은 "교차점")처럼 맞는 사진도 가끔 놓친다.

#### 사진이 없는 줄이 섞인다

87% 는 다섯 곳 중 한 곳쯤은 사진이 없다는 뜻이다. 그 줄은 사진 없이 나간다 — 호텔도 썸네일을 못 구하면 같은 모양이라 새로운 상태는 아니다. **사진을 못 구했다고 그 관광지를 목록에서 빼지는 않는다.** 추천 자체가 사라지는 게 사진 한 장 없는 것보다 나쁘다.

콜백 경로에서만 도는 코드라 5초 예산과 무관하고, 5곳을 동시에 찾는다. 결과는 검색 캐시에 같이 저장되므로 같은 도시를 다시 물어도 API 를 또 치지 않는다. 끄려면 `ATTRACTION_IMAGES=false`.

#### ⚠️ 저작권 — 지금은 카드 단위 출처 표시뿐이다

위키미디어 사진은 대부분 CC BY-SA 라 **엄밀히는 사진마다 저작자와 라이선스를 밝혀야 한다.** listCard 한 줄에는 링크가 하나뿐이고 그 자리는 지도가 써야 해서(클릭 추적) 줄마다 출처를 달 자리가 없다. 지금은 카드 하단에 "사진 출처: 위키미디어" 버튼 하나를 단다 — 출처가 어디인지만 알리는 수준이고 정식 표시는 아니다.

사진을 카드 밖(웹·앱·광고)에서 쓰게 되면 그때는 제대로 된 표시가 필요하다. `extmetadata` 로 저작자·라이선스를 같이 받아올 수 있으니, 표시할 자리가 생기면 그때 붙이면 된다.

## 7. DB

새 테이블이 없다. `domain='attraction'` 이 가른다. 컬럼 의미는 [`0003_attraction.sql`](../supabase/migrations/0003_attraction.sql) 주석이 원본이고, 요약하면:

| 컬럼 | 관광지일 때 |
|---|---|
| `affiliate_link_id` | **항상 null** (제휴 링크를 타지 않는다) |
| `source_url` | 구글맵 주소. 이름+도시로 결정되므로 관광지의 신원이다 |
| `target_url` | 같은 값 — 중간에 변환이 없다 |
| `hotel_name` | 관광지명 |
| `price_from` | **항상 null** ← 아래 참고 |
| `thumbnail_url` | 항상 null |
| `recommendations.guests` | 항상 null (인원 개념이 없다) |

### 입장료를 `price_from` 에 넣지 않는 이유

그 칸은 호텔 1박가·항공 운임이 들어가는 자리이고 단위가 **원**이다. 관광지 입장료는 현지 통화라 같은 칸에 넣으면 비교 불가능한 숫자가 섞인다 — 통화 컬럼도 없으므로 나중에 누가 합계를 내면 **조용히 틀린다.**

입장료는 카드와 `search_cache` 에만 남긴다. 환율 API 로 원화를 확정할 수 있게 되면 그때 채우면 된다.

### ⚠️ 수익 집계에서 관광지를 빼야 한다

제휴 링크가 없어 구조적으로 수수료가 0 이다. 도메인을 섞어서 전환율을 내면 커미션 도메인이 실제보다 나빠 보인다. `0003_attraction.sql` 끝에 도메인별 집계 SQL 예시를 넣어뒀다.

## 10. 알려진 한계

### 입장료·소요 시간은 참고값이다

웹 검색 결과라 틀릴 수 있다. 실측에서 오사카성이 `600엔` 으로 나온 적이 있다(실제 1,200엔 — 아마 구버전 요금이나 부분 입장료를 집은 것). 통화 단위는 이제 맞지만 **숫자 자체의 정확도는 보장되지 않는다.**

호텔·항공권과 달리 이 오차의 대가는 작다(예약이 아니라 방문 계획이고, 현장에서 실제 요금을 본다). 그래도 "5,000원짜리" 로 알고 갔다가 2만원을 내는 일은 있을 수 있다.

| 한계 | 지금 상태 |
|---|---|
| 입장료 정확도 | 검색 시점 웹 결과. 할인·성수기·부분 입장은 반영 안 됨 |
| 지역(area) 표기 | 모델이 흔들린다. 특히 비한자권 지명의 한글 표기(`앙깡/시내`) |
| 휴관일·영업시간 | 미지원. 지도 링크의 장소 카드에서 확인하게 둔다 |
| 테마 검색 | 미지원 ("아이랑", "야경"). 캐시 키 설계가 먼저다 (3절) |
| 카드 이미지 | **실측 87%.** 나머지는 사진 없이 나간다 (6절) |
| 사진 저작권 표시 | 카드 단위 출처 버튼뿐. 사진별 저작자·라이선스 표시는 없다 (6절) |
| 동선·거리 | 미지원. 서로 가까운 곳끼리 묶어주지 않는다 |

### 다음 단계

- **사진 커버리지** — 남는 13% 는 위키백과에 문서가 없는 곳들이다. 구글 Places 사진 API 가 다음 후보지만 키와 요금이 붙는다
- **사진별 저작권 표시** — `extmetadata` 로 저작자·라이선스를 받아올 수 있다. 표시할 자리(카드 구조)가 먼저다
- **테마 파싱** — 캐시 키에 테마 축을 먼저 넣어야 한다
- **영업시간·휴관일** — 40자 한 줄에 자리가 없다. 카드 구조부터 다시 봐야 한다
