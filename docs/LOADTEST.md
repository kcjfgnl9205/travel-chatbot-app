# 부하 시험

> 대상: `https://bot.nolmoa.com` (Cloudflare → nginx → `127.0.0.1:8000`)
> 서버: **Oracle Cloud `VM.Standard.A1.Flex`** — OCPU 1 · RAM 6GB · ARM64(Ampere) ·
> `ap-chuncheon-1` 춘천 · Ubuntu 24.04
> DB: **OCI MySQL HeatWave** (Always Free) · AI: OpenAI
> 하네스: [`loadtest/`](../loadtest/) ([돌리는 법](../loadtest/README.md))

**한 줄 결론: 동시 800명까지 안전하고 1000명에서 무너진다. 처리량 천장은 약 300 req/s 다.
2026-11-03 에는 이 숫자가 20명 / 8.5 req/s 였다 — 40배가 됐고, 그 사이 병목이 세 번 옮겨갔다.**

| 날짜 | 구성 | 안전 동시 | 붕괴 | 천장 | 그때의 병목 |
|---|---|---:|---:|---:|---|
| 11-03 | 도쿄 + Supabase | 20명 | ~34명 | 8.5 req/s | **DB 왕복** |
| 11-04 오전 | 춘천 + MySQL | 300명 | ~400명 | 285 req/s | **nginx 앞문** |
| 11-04 오후 | + nginx 수정 | **800명** | **1000명** | **~300 req/s** | **앱 (OCPU 1)** |

## 1. 왜 평범한 부하 시험으로는 이 서비스를 못 재는가

**여기서 "못 버틴다" 는 500 이 아니다.**

카카오는 5초를 넘긴 응답을 버린다. 그 전에 앱이 스스로
`KAKAO_RESPONSE_BUDGET_SECONDS`(3.5초)에서 끊고 도움말 카드를 보낸다
([`router.controller.ts`](../src/modules/kakao/router.controller.ts) 의 `withinBudget`).

그래서 서버가 한계에 닿아도 **HTTP 는 전부 200 이고 에러율은 0% 다.**
사용자에게 보이는 고장은 "이해하지 못했어요" 라는 멀쩡한 카드다.

> ⚠️ 상태코드·에러율만 보는 부하 시험이었다면, **사용자 98% 가 답을 못 받는 상태를
> "정상" 으로 읽었을 것이다.** 실제로 11-03 의 VU 40 에서 HTTP 실패는 0.0% 였다.

그래서 이 하네스는 상태코드가 아니라 **응답 본문을 분류한다.**

| 분류 | 본문 신호 | 뜻 |
|---|---|---|
| `card` | `listCard` | 정상. 저장된 결과가 나갔다 |
| `help` | `이해하지 못했어요` | 의도 불명(정상) **또는** 예산 초과 |
| `budget_cut` | `help` + 응답시간 ≥ 예산×0.9 | ⚠️ **진짜 고장. 이것만 센다** |
| `searching` | `찾고 있어요` | 캐시 미스 — 백그라운드 검색 시작 |
| `busy` | `먼저 찾고 있어요` | 같은 키를 다른 요청이 선점 (부하에서는 정상) |
| `app_down` | `점검 중` | ⚠️⚠️ nginx 폴백. 앱에 **아예 못 붙었다** |

`help` 와 `budget_cut` 을 가르는 게 핵심이다. **본문이 같고 시간이 다르다.**

> ⚠️ **그런데 이것만으로도 부족했다.** 11-04 에 **HTTP 실패**로 무너지는 구간을
> 만났는데(Cloudflare 525), 그건 `app_down` 에도 `budget_cut` 에도 안 잡힌다 —
> 앱은 멀쩡하고 예산도 안 넘기 때문이다. 요청이 앱에 **닿지를 못한** 것이다.
> `run.sh` 에 `ABORT_FAIL`(기본 5%)을 뒤늦게 더했다. 4절 참조.

## 3. 병목이 세 번 옮겨갔다

### 3-1. Supabase DB 왕복 (11-03) → MySQL 이전으로 해결

11-03 시험의 천장은 8.5 req/s 였고, **서버를 5배로 키워도 안 움직였다.**

| VU | 이전 서버 `/health` | 도쿄 서버 `/health` |
|---:|---|---|
| 50 | 98.3 req/s | **505.1 req/s** (5배) |

| VU | 이전 챗봇 | 도쿄 챗봇 |
|---:|---|---|
| 20 | 9.9 req/s | **8.4 req/s** (제자리) |

**서버 성능 5배 ↑, 챗봇 처리량 제자리.** 범인은 서버가 아니라 요청당 DB 왕복
7회였고, Supabase 무료 티어(Nano)가 **약 34 쿼리/s 에서 포화**했다.

| 동시 | Supabase 건당 | 유효 처리량 |
|---:|---:|---:|
| 1 | 122ms | 8.2/s |
| 6 | 214ms | 26.0/s |
| 12 | 267ms | 35.8/s |
| 24 | 436ms | **34.0/s** |

**MySQL HeatWave 로 옮긴 뒤 같은 측정:**

| 동시 | 쿼리/s | p50 | 포화 |
|---:|---:|---:|---|
| 1 | 75 | 122ms | — |
| 10 | 789 | 122ms | — |
| 20 | **1,565** | 122ms | **없음** |

**46배를 넣어도 지연이 안 올라간다.** 서버 안에서 잰 DB 왕복은 10테이블 병렬에
**3~5ms** 다 (Supabase 때 6개 병렬 ~400ms). 진단이 맞았음이 증명됐다.

> p50 122ms 는 DB 가 아니라 **측정자→서버 네트워크 왕복**이다. `/health/db` 응답의
> `latencyMs` 가 서버 안에서 쓴 시간이고 그게 3~5ms 다.

### 3-2. nginx 앞문 (11-04 오전) → 설정으로 해결

DB 를 고치자 천장이 285 req/s 로 뛰었는데, **동시 400 부터 HTTP 실패가 시작됐다.**

| VU | 수정 전 HTTP 실패 | 수정 후 |
|---:|---:|---:|
| 300 | 0.0% | 0.0% |
| 400 | **15.6%** | **0.0%** |
| 500 | **76.8%** | **0.0%** |
| 600 | (못 가봄) | 0.0% |

실패는 전부 **Cloudflare 525 — 오리진 TLS 핸드셰이크 실패**였다.

```
HTTP 525  cf-ray=a54fafac6c586c47-HKG  body=error code: 525
   정상(2xx)   2958   42.8%
   5xx         3960   57.2%   ← 전부 525
   429 제한       0    0.0%
```

**그동안 앱은 에러를 한 번도 안 냈고 DB 왕복은 3ms 였다.** 요청이 앱까지 도착조차
못 한 것이다.

범인은 `/etc/nginx/nginx.conf` 의 **`worker_connections 768`** 로 보인다.
`worker_processes auto` 는 OCPU 1개라 worker 1개이고, 프록시는 요청당 연결을
둘 쓴다(클라이언트 + 업스트림) — 즉 **동시 클라이언트 상한 약 384**. 측정값과 맞는다.

| | |
|---|---|
| 768 ÷ 2 = **384** | ← 이론 상한 |
| 300 → 100% 정상, 400 → 15.6% 실패 | ← 실측 |

고친 것 ([`deploy/nginx/bot-nolmoa.conf`](../deploy/nginx/bot-nolmoa.conf), 커밋 `75819ba`·`7fba064`):

1. `worker_connections` 768 → 4096 *(서버의 `nginx.conf`, 저장소 밖)*
2. `net.core.somaxconn` 4096 *(안 올리면 `backlog` 가 조용히 잘린다)*
3. `ssl_session_cache` / `ssl_session_tickets` — TLS 세션 재사용
4. `upstream app { keepalive 64; }` + `proxy_set_header Connection "";`

### 3-3. 이제 앱 자신 (OCPU 1)

처리량 ~300 req/s 가 현재 천장이고, 이건 **1 OCPU 가 카드 JSON 을 만드는 비용**이다.
근거: `/health`(DB 안 붙음)는 387 req/s 까지 나왔는데 라우터는 285~310 에서 멈춘다.
측정자 쪽 네트워크가 387 은 냈으므로 **라우터 천장은 서버 쪽**이다.

더 올리려면 OCPU 를 늘리거나 요청당 비용을 줄여야 한다. **현재 트래픽(하루 6~30건)
에서는 할 이유가 없다.**

## 4. ⚠️ 이 문서가 틀렸던 것들

**같은 실수를 세 번 했다. 전부 "숫자 하나로 메커니즘을 단정" 한 것이고,
전부 대조군을 만들고 나서야 깨졌다.**

| # | 틀린 주장 | 근거로 쓴 것 | 무엇이 깼나 |
|---|---|---|---|
| 1 | "범인은 1 vCPU 다" | `/health` 98 req/s | 서버를 5배로 키웠더니 **용량이 제자리** |
| 2 | "동시 연결이 3개로 묶여 있다" | `/health/db` 6병렬 400ms | 직접 재보니 **연결 수가 아니라 처리량** 한계 |
| 3 | "525 의 원인은 TLS 세션 캐시" | 설정 파일에 그 줄이 없음 | `nginx.conf` 를 보니 **`worker_connections 768`** 이 숫자와 맞음 |

3번은 특히 — **저장소 파일만 보고 가설을 세웠고, 서버의 `nginx.conf` 를 안 봤다.**
그리고 고칠 때 네 가지를 한꺼번에 반영했기 때문에 **어느 것이 효과를 냈는지는
이 측정으로 구분되지 않는다.** 숫자상 `worker_connections` 가 유력하지만 증명은 아니다.

> **대조군 없이 메커니즘을 적지 말 것.** 적어야 한다면 "가설" 이라고 쓸 것.

## 5. 비용은 0원이다

의도 해석은 3단이다 — **캐시 → 키워드+도시 사전 → 모델**
([`intent.service.ts`](../src/modules/intent/intent.service.ts)). `"오사카 호텔 추천해줘"` 는
2단에서 끝나 **모델을 아예 안 부른다.** 검색 결과도 DB 에 저장돼 있다.

> **단, 캐시를 안 채우고 돌리면 측정 대상이 서버 용량이 아니라 OpenAI 대기열이 되고
> 비용이 요청 수만큼 난다.** `warmup.sh` 를 건너뛰지 말 것.

## 6. ⚠️ 이 시험은 서버를 한 번 죽였다 (2026-10-27, 이전 서버)

**250 VU 구간에서 VM 이 응답 불능이 되었고, 부하를 멈춘 뒤에도 자동 복구되지
않았다.** 40회 확인했고 전부 실패(`Cloudflare 522`). 최소 43분.

> 앱 컨테이너만 죽었다면 nginx 가 "점검 중"(`@kakao_down`)을 돌려줬어야 한다.
> 그게 안 나왔다 = **nginx 까지 안 닿는다** = VM 자체가 죽었다. RAM 1GB 였으므로
> OOM 이 유력하다.

**그날과 11-04 의 차이가 교훈이다.** 11-04 에는 1000 VU 까지 밀었는데도 서버가
살아남았다:

| | 10-27 (죽음) | 11-04 (생존) |
|---|---|---|
| 자동 중단 | **껐음** (`ABORT_HELP=90`) | **켬** (실패 5% / 예산잘림 25% / 앱다운 1회) |
| RAM | 1GB | 6GB |
| 복구 수단 | **없었음** (SSH 불가) | SSH 확보 |
| 결과 | 43분 다운 | `app_down` 0회, 직후 정상 |

### 다음에 지킬 것

1. **복구 수단을 먼저 확보한다.** SSH 가 안 되는 상태로 한계까지 밀지 않는다
2. `run.sh` 의 자동 중단을 **끄지 않는다.** 11-04 에 `ABORT_FAIL` 이 1000 VU 에서
   실제로 작동해 거기서 멈췄다 — 그게 설계대로 돈 모습이다
3. 운영 트래픽이 있을 때는 **10 VU 를 넘기지 않는다**

## 8. 남은 것

- **지속 부하를 안 쟀다.** 전부 30초짜리다. 1000 VU 가 몇 분 지속될 때 메모리가
  어떻게 되는지는 모른다
- **캐시 미스(AI) 경로는 재지 않았다.** 20~30초짜리 백그라운드 작업이라 동시성
  측정 대상이 아니고, 요청 수만큼 돈이 나간다
- **nginx 수정 네 가지 중 무엇이 효과를 냈는지 모른다.** 한꺼번에 반영했다
- **Cloudflare 가 한국 트래픽을 홍콩(HKG)으로 보낸다.** `/cdn-cgi/trace` 에서
  `colo=HKG`, `loc=KR` 이 나온다. 측정자 왕복 ~120ms 의 대부분이 이 우회이고,
  **실사용자도 같은 길을 돌고 있을 수 있다.** 서버를 춘천으로 옮긴 효과를
  깎아먹는 셈이라 따로 확인할 가치가 있다
- **외부 다운타임 감시가 없다.** 10-27 장애를 43분간 아무도 몰랐다
