# 부하 시험 — 2026-10-27

> 대상: `https://bot.nolmoa.com` (Cloudflare → nginx → `127.0.0.1:8000`)
> 서버: Oracle Cloud `mi1-g3` — **vCPU 1 · RAM 1GB** · DB: Supabase · AI: OpenAI
> 하네스: [`loadtest/`](../loadtest/) (돌리는 법은 [`loadtest/README.md`](../loadtest/README.md))

**한 줄 결론: 동시 20명까지 안전하고, 34명 근처에서 무너진다. 처리량 천장은 10 req/s 이고, 범인은 DB 가 아니라 1 vCPU 다.**

## 1. 왜 평범한 부하 시험으로는 이 서비스를 못 재는가

**여기서 "못 버틴다" 는 500 이 아니다.**

카카오는 5초를 넘긴 응답을 버린다. 그 전에 앱이 스스로
`KAKAO_RESPONSE_BUDGET_SECONDS`(3.5초)에서 끊고 도움말 카드를 보낸다
([`router.controller.ts`](../src/modules/kakao/router.controller.ts) 의 `withinBudget`).

그래서 서버가 한계에 닿아도 **HTTP 는 전부 200 이고 에러율은 0% 다.**
사용자에게 보이는 고장은 "이해하지 못했어요" 라는 멀쩡한 카드다.

> ⚠️ 상태코드·에러율만 보는 부하 시험이었다면, **사용자 93% 가 답을 못 받는 상태를
> "정상" 으로 읽었을 것이다.** 실제로 VU 40 에서 HTTP 실패는 0.0% 였다.

그래서 이 하네스는 상태코드가 아니라 **응답 본문을 분류한다.**

| 분류 | 본문 신호 | 뜻 |
|---|---|---|
| `card` | `listCard` | 정상. 저장된 결과가 나갔다 |
| `help` | `이해하지 못했어요` | 의도 불명(정상) **또는** 예산 초과 |
| `budget_cut` | `help` + 응답시간 ≥ 예산×0.9 | ⚠️ **진짜 고장. 이것만 센다** |
| `searching` | `찾고 있어요` | 캐시 미스 — 백그라운드 검색 시작 |
| `busy` | `먼저 찾고 있어요` | 같은 키를 다른 요청이 선점 (부하에서는 정상) |
| `app_down` | `점검 중` | ⚠️⚠️ nginx 폴백. 앱에 **아예 못 붙었다** |

`help` 와 `budget_cut` 을 가르는 게 핵심이다. **본문이 같고 시간이 다르다** —
"안녕" 에 대한 정상 도움말은 240ms 에 나오고, 예산에서 잘린 도움말은 3.5초를
꽉 채우고 나온다.

## 3. 해석

### 처리량 천장은 10 req/s 다

VU 를 5 → 40 으로 **8배** 올려도 처리량은 7.7 → 10.8 req/s 로 **1.4배**에 그친다.
나머지는 전부 대기열로 간다. 리틀의 법칙이 소수점까지 들어맞는다:

| VU | 예측 지연 (VU ÷ 처리량) | 실측 p50 |
|---:|---:|---:|
| 10 | 10 ÷ 9.5 = 1.05초 | 1.03초 |
| 20 | 20 ÷ 9.9 = 2.02초 | 1.94초 |
| 40 | 40 ÷ 10.8 = 3.70초 | 3.64초 |

**3.5초 예산을 넘는 지점은 동시 34건 근처다.** 20 VU 에서 p95 2.67초로 아직 여유가
있고, 40 VU 에서 93% 가 도움말 카드를 받는다.

> "동시 N명" 은 접속자 수가 아니라 **그 순간 처리 중인 요청 수**다. 카카오 챗봇은
> 연결을 붙들지 않으므로, 실제로 중요한 건 **초당 도착률(10 req/s)** 이다.

### 병목은 Supabase 가 아니라 1 vCPU 다

이게 `/health` 기준선을 같이 잰 이유다. **같은 Cloudflare 경로**인데:

- `/health` (DB·AI 미접촉) → **98 req/s**
- `/api/v1/kakao/router` (저장된 카드) → **10 req/s**

같은 경로이므로 **Cloudflare 도 네트워크도 범인이 아니다.** 10배 차이는 라우터가
요청당 더 쓰는 것이고, 그게 CPU 다 — 1 vCPU ÷ 10 req/s = **요청당 약 100ms 의 동기 작업**.
Supabase 왕복은 비동기라 동시성을 막지 않는다. 막는 건 JSON 파싱·카드 조립·해시
같은 이벤트루프 점유 작업이다.

무부하 지연 **533ms** 는 별개 문제다. 이건 CPU 가 아니라 요청당 Supabase 왕복 횟수다
(사용자 등록 → 장소 해석 → 검색 캐시 조회 → 메시지 로그).

### 예산 컷이 로드 셰딩으로 작동한다

VU 100 에서 처리량이 오히려 **26 req/s 로 올랐다.** 3.5초에 끊고 싼 도움말 카드를
내보내면서 무거운 일을 버린 것이다. 의도한 설계는 아니지만 **결과적으로 앱을 지켰다** —
250 VU 까지 `app_down` 이 0 이었다 (즉 Node 프로세스는 끝까지 살아 있었다).

### 비용은 0원이었다

의도 해석은 3단이다 — **캐시 → 키워드+도시 사전 → 모델**
([`intent.service.ts`](../src/modules/intent/intent.service.ts)). `"오사카 호텔 추천해줘"` 는
2단에서 끝나 **모델을 아예 안 부른다.** 10개 도시의 검색 결과도 실사용으로 이미
캐시에 차 있어서 워밍업에서도 OpenAI 호출이 0회였다.

> 부하 단계가 공짜라는 뜻이다. **단, 캐시를 안 채우고 돌리면 측정되는 건 서버 용량이
> 아니라 OpenAI 대기열이고, 비용이 요청 수만큼 나간다.** 워밍업을 건너뛰지 말 것.

## 4. ⚠️ 이 시험은 운영 서버를 죽였다

**250 VU 구간(14:46)에서 VM 이 응답 불능이 되었고, 부하를 멈춘 뒤에도 자동 복구되지
않았다.** `Cloudflare 522` (CF 가 오리진에 TCP 연결조차 못 함) 가 계속됐다.

> **14:46 ~ 최소 15:28 (43분) 다운.** 그 사이 40회 확인했고 전부 실패했다 —
> **자동 복구되지 않는다.** 이후 수동 개입으로 복구됐다 (2026-11-02 정상 확인).
>
> ⚠️ **다운의 직접 원인은 아직 모른다.** 서버에서 `dmesg | grep -i oom` 을 확인해야
> 한다. OOM 흔적이 있으면 범인은 메모리(1GB)이고, 없으면 CPU 고갈로 인한 스래싱이다.
> **측정에서는 CPU 병목으로 나왔지만 다운의 원인은 별개일 수 있고, 증설 방향이 갈린다.**

진단의 핵심:

> 앱 컨테이너만 죽었다면 nginx 가 살아서 "점검 중" 말풍선(`@kakao_down`)을 돌려줬어야
> 한다. 그게 안 나왔다 = **nginx 까지 안 닿는다** = VM 자체가 죽었다.
> 1 vCPU 고갈 또는 1GB OOM 으로 인한 스래싱으로 추정된다.

`docker compose` 의 `restart: unless-stopped` 도, nginx 폴백도 **VM 이 살아 있어야
작동한다.** 둘 다 이 사고를 막지 못했다.

### 다음에 지킬 것

1. **복구 수단을 먼저 확보한다.** SSH 접속이 안 되는 상태로 한계까지 밀지 않는다.
   이번에는 접속 정보가 GitHub Secrets 에만 있어서 콘솔 재부팅 외에 길이 없었다
2. **40 VU 에서 멈췄어야 했다.** 거기서 이미 답(93% 도움말)이 나왔다. 100·250 은
   "얼마나 더 나빠지나" 만 알려줬고 그 대가가 서버 다운이었다
3. `run.sh` 의 자동 중단(`ABORT_HELP`, 기본 25%)을 **끄지 않는다.** 이번엔 90으로
   올려서 무력화했다
4. 운영 트래픽이 있을 때는 **10 VU 를 넘기지 않는다** (p95 1.3초, 예산잘림 0%)


부하 중 서버에서 같이 볼 것 — **무엇이 먼저 무너지는지는 밖에서 안 보인다**:

```bash
docker stats --no-stream                          # CPU 100% = vCPU 포화, MEM 1GB = OOM 임박
docker compose logs -f app | grep -E '예산|ms='   # 예산 초과 로그와 구간별 소요
```

## 6. 남은 것

- **요청당 100ms CPU 가 어디서 나는지 모른다.** 밖에서는 못 가른다. 서버에서
  `--cpu-prof` 또는 구간별 타이머가 필요하다. 이걸 줄이는 게 천장을 올리는 유일한 길이다
- **무부하 533ms 의 Supabase 왕복 횟수를 세지 않았다.** 병렬화할 수 있는 왕복이
  직렬로 도는지 확인할 가치가 있다
- **캐시 미스(AI) 경로는 재지 않았다.** 20~30초짜리 백그라운드 작업이라 동시성 측정
  대상이 아니고, 요청 수만큼 돈이 나간다
- **오리진 직접(`127.0.0.1:8000`) 측정을 못 했다.** SSH 가 없었다. `/health` 대조군으로
  Cloudflare 를 용의선상에서 지웠으므로 급하지는 않다
