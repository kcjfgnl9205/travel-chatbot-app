# 부하 시험

> 대상: `https://bot.nolmoa.com` (Cloudflare → nginx → `127.0.0.1:8000`)
> 서버: **Oracle Cloud `VM.Standard.A1.Flex`** — OCPU 1 · RAM 6GB · ARM64(Ampere) ·
> `ap-tokyo-1` · Ubuntu 24.04
> DB: Supabase · AI: OpenAI · 하네스: [`loadtest/`](../loadtest/) ([돌리는 법](../loadtest/README.md))

**한 줄 결론: 동시 20명까지 안전하고 34명 근처에서 무너진다. 처리량 천장은 8.5 req/s 이고,
범인은 서버가 아니라 요청당 DB 왕복 7회다 — 서버를 5배로 키워도 안 움직였다.**

---

## 1. 왜 평범한 부하 시험으로는 이 서비스를 못 재는가

**여기서 "못 버틴다" 는 500 이 아니다.**

카카오는 5초를 넘긴 응답을 버린다. 그 전에 앱이 스스로
`KAKAO_RESPONSE_BUDGET_SECONDS`(3.5초)에서 끊고 도움말 카드를 보낸다
([`router.controller.ts`](../src/modules/kakao/router.controller.ts) 의 `withinBudget`).

그래서 서버가 한계에 닿아도 **HTTP 는 전부 200 이고 에러율은 0% 다.**
사용자에게 보이는 고장은 "이해하지 못했어요" 라는 멀쩡한 카드다.

> ⚠️ 상태코드·에러율만 보는 부하 시험이었다면, **사용자 98% 가 답을 못 받는 상태를
> "정상" 으로 읽었을 것이다.** 실제로 VU 40 에서 HTTP 실패는 0.0% 였다.

그래서 이 하네스는 상태코드가 아니라 **응답 본문을 분류한다.**

| 분류 | 본문 신호 | 뜻 |
|---|---|---|
| `card` | `listCard` | 정상. 저장된 결과가 나갔다 |
| `help` | `이해하지 못했어요` | 의도 불명(정상) **또는** 예산 초과 |
| `budget_cut` | `help` + 응답시간 ≥ 예산×0.9 | ⚠️ **진짜 고장. 이것만 센다** |
| `searching` | `찾고 있어요` | 캐시 미스 — 백그라운드 검색 시작 |
| `busy` | `먼저 찾고 있어요` | 같은 키를 다른 요청이 선점 (부하에서는 정상) |
| `app_down` | `점검 중` | ⚠️⚠️ nginx 폴백. 앱에 **아예 못 붙었다** |

`help` 와 `budget_cut` 을 가르는 게 핵심이다. **본문이 같고 시간이 다르다** —
"안녕" 에 대한 정상 도움말은 170ms 에 나오고, 예산에서 잘린 도움말은 3.5초를
꽉 채우고 나온다.

## 3. 병목은 서버가 아니다 — 서버를 5배로 키워 증명했다

2026-10-27 에 **이전 서버(vCPU 1 · RAM 1GB)** 에서 같은 시험을 돌렸고,
11-02 에 현재 서버로 옮긴 뒤 **같은 조건으로 다시 돌렸다.** 그 대조가 답을 줬다.

### 서버 자체 성능 — 5배 빨라졌다

`/health` 는 DB 도 AI 도 안 건드린다. 순수 앱·서버 용량이다.

| VU | 이전 서버 | **현재 (Oracle)** |
|---:|---|---|
| 10 | 82.6 req/s · p95 190ms | **133.4 req/s · p95 124ms** |
| 50 | 98.3 req/s · p95 296ms · 실패 3.8% | **505.1 req/s · p95 179ms · 실패 0%** |

### 그런데 챗봇 용량은 그대로다

| VU | 이전 p50 | 현재 p50 | 이전 req/s | 현재 req/s |
|---:|---:|---:|---:|---:|
| 1 | 533ms | **342ms** | 1.8 | 2.3 |
| 5 | 627ms | 605ms | 7.7 | 8.1 |
| 10 | 1028ms | 1160ms | 9.5 | 8.5 |
| 20 | 1935ms | 2338ms | 9.9 | 8.4 |
| 40 | 3636ms | 3634ms | 10.8 | 10.9 |

**서버 성능 5배 ↑, 챗봇 처리량 천장 9.5 → 8.5 req/s (제자리).**
안전선 20명, 붕괴 40명도 그대로다.

> ⚠️ **이 문서는 예전에 "범인은 1 vCPU 다" 라고 적고 있었다. 틀렸다.**
> 근거로 쓴 `/health` 98 req/s 가 사실은 **그 서버 자체의 천장**이어서, 서로 다른 두
> 한계를 하나로 착각한 것이다. 서버를 바꿔보니 드러났다 — **서버를 키워도 용량은 안 는다.**

### 범인은 요청당 DB 왕복이다

왕복 수가 다른 경로를 나란히 재면 비용이 드러난다.

| 경로 | DB 왕복 | 응답시간(p50) | 왕복당 |
|---|---:|---:|---:|
| `/health` | 0회 | 51ms | — (네트워크 기준선) |
| 라우터 `"안녕"` | 1~2회 | 170ms | ~60ms |
| 라우터 카드 | 약 7회 | 376ms | **~46ms** |

**왕복 1회가 약 50ms 이고 그게 그대로 더해진다.** 7번이면 350ms —
3.5초 예산의 10% 를 무부하에서 이미 쓴다.

### ⚠️ 병렬이 병렬로 안 돈다

`/health/db` 는 테이블 **6개를 `Promise.all` 로 동시에** 조회한다. 진짜 병렬이면
1개 조회(~50ms)와 비슷해야 한다.

**실측 364~421ms.** 6개를 하나씩 줄 세운 것과 같다.

역산하면 Supabase 로 나가는 **동시 연결이 약 3개**로 묶여 있다
(8.5 req/s × 7왕복 × 50ms ≈ 3). 이것이 처리량 천장 8.5 req/s 의 정체다.

> **Supabase 가 거절하는 게 아니다.** Supabase 는 이보다 훨씬 많이 처리한다.
> 연결이 그만큼만 열리는 것으로 보이는데, 원인이 Node 의 HTTP 커넥션 풀인지
> Supabase 쪽 풀러인지는 **밖에서는 못 가린다.** 서버 안이나 코드를 봐야 한다.

### 그래서 할 일의 순서

| 순위 | 조치 | 기대 효과 | 비용 |
|---|---|---|---|
| 1 | **요청당 왕복 7회를 줄인다** | 왕복 반 → 한계 약 2배 | 코드 |
| 2 | **동시 연결 수를 확인·상향한다** | 풀이 범인이면 몇 배 | 설정 한 줄일 수도 |
| 3 | ~~서버 증설~~ | **0 (증명됨)** | 돈만 |

## 4. 비용은 0원이다

의도 해석은 3단이다 — **캐시 → 키워드+도시 사전 → 모델**
([`intent.service.ts`](../src/modules/intent/intent.service.ts)). `"오사카 호텔 추천해줘"` 는
2단에서 끝나 **모델을 아예 안 부른다.** 검색 결과도 Supabase 에 저장돼 있어
서버를 갈아도 캐시는 따뜻하다.

> **단, 캐시를 안 채우고 돌리면 측정 대상이 서버 용량이 아니라 OpenAI 대기열이 되고
> 비용이 요청 수만큼 난다.** `warmup.sh` 를 건너뛰지 말 것.

## 5. ⚠️ 이 시험은 서버를 한 번 죽였다 (2026-10-27, 이전 서버)

**250 VU 구간(14:46)에서 VM 이 응답 불능이 되었고, 부하를 멈춘 뒤에도 자동 복구되지
않았다.** 40회 확인했고 전부 실패(`Cloudflare 522`)였다. 최소 43분.

> 앱 컨테이너만 죽었다면 nginx 가 "점검 중" 말풍선(`@kakao_down`)을 돌려줬어야 한다.
> 그게 안 나왔다 = **nginx 까지 안 닿는다** = VM 자체가 죽었다. RAM 1GB 였으므로
> OOM 이 유력하다. **현재 서버는 6GB 라 같은 방식으로는 죽지 않을 가능성이 높다** —
> 실제로 11/03 시험의 60 VU 에서 앱다운 0, HTTP 실패 0% 였다.

### 다음에 지킬 것

1. **복구 수단을 먼저 확보한다.** SSH 가 안 되는 상태로 한계까지 밀지 않는다
2. **40 VU 에서 멈춘다.** 거기서 이미 답이 나온다. 100·250 은 "얼마나 더 나빠지나" 만
   알려주고 그 대가가 장애였다
3. `run.sh` 의 자동 중단(`ABORT_HELP`, 기본 25%)을 **끄지 않는다**
4. 운영 트래픽이 있을 때는 **10 VU 를 넘기지 않는다**

## 6. 다시 재는 법

```bash
./loadtest/warmup.sh                        # 검색 캐시 선채움 (비면 OpenAI 비용 발생)
VUS=20 k6 run loadtest/health.js            # 기준선 — 병목이 서버인지 가르는 대조군
STEPS="1 5 10 20 40" ./loadtest/run.sh      # 본 시험 (자동 중단 켜둔 채로)
```

부하 중 서버에서 같이 볼 것 — **무엇이 먼저 무너지는지는 밖에서 안 보인다**:

```bash
docker stats --no-stream                          # CPU·메모리 포화 확인
docker compose logs -f app | grep -E '예산|ms='   # 예산 초과 로그와 구간별 소요
```

## 7. 남은 것

- **왕복 7회가 각각 무엇인지 세지 않았다.** 합치거나 캐시할 수 있는 게 있는지가
  용량을 늘리는 유일한 길이다 (3절 참조)
- **동시 연결 3개의 원인을 모른다.** Node 의 fetch 풀인지 Supabase 풀러인지.
  서버 안에서 봐야 한다
- **캐시 미스(AI) 경로는 재지 않았다.** 20~30초짜리 백그라운드 작업이라 동시성
  측정 대상이 아니고, 요청 수만큼 돈이 나간다
- **Supabase 리전을 확인하지 않았다.** 서버가 `ap-tokyo-1` 이므로, Supabase 가 서울이면
  왕복 50ms 중 상당 부분이 그 거리다
