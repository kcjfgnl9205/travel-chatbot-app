# 부하 시험 결과 요약 (기획용)

> 2026-11-04 측정 · 대상: 운영 중인 가자고 챗봇 서버
> (Oracle Cloud · OCPU 1 · RAM 6GB · 춘천 리전 · DB: OCI MySQL HeatWave)
> 기술 상세는 [LOADTEST.md](LOADTEST.md)

---

## 세 줄 요약

1. **동시에 800명까지 문제없다.** 1000명에서 무너진다.
   하루 전만 해도 이 숫자가 **20명**이었다 — **40배**가 됐다
2. **무너져도 서버가 죽지는 않는다.** 답을 못 줄 뿐이고, 부하가 빠지면 즉시 돌아온다
3. **무너지는 방식이 여전히 위험하다.** 에러가 아니라 "이해하지 못했어요" 로 나간다 —
   **사용자는 서버가 아픈 걸 모르고 봇이 멍청하다고 느낀다**

---

## 1. 얼마나 버티나

"동시 N명" 은 **같은 순간에 봇에게 말을 걸어 답을 기다리는 사람 수**다.

| 동시 사용자 | 답변까지 | 제대로 답한 비율 | 판정 |
|---:|---:|---:|:--|
| 10명 | 0.1초 | 100% | 쾌적 |
| 100명 | 0.4초 | 98% | 쾌적 |
| 300명 | 1.0초 | 100% | 양호 |
| 500명 | 1.6초 | 100% | 양호 |
| **800명** | **2.7초** | **98.5%** | **여기까지가 안전선** |
| 900명 | 2.9초 | — | 경고 — 일부가 제한 시간을 넘기기 시작 |
| **1000명** | 3.6초 | **31%** | **붕괴 — 69% 가 답을 못 받음** |

**목표로 하던 100~300명 대비 2.7배 여유가 있다.**

처리량으로 바꾸면 **1초에 약 300건, 1분에 18,000건**이 이 서버의 최대치다.
사람을 더 밀어 넣어도 처리량은 안 늘고 **대기줄만 길어진다.**

> 놀이공원 매표소 비유 — 창구는 1초에 300명을 처리한다. 줄이 800명이면 2.7초
> 기다리고, 1000명이면 3.6초를 기다리는데 **카카오톡이 5초에서 끊기** 때문에
> 그 지점부터 사람들이 답을 못 받고 돌아간다.

### "1000명 넘으면 서버가 터지나?" — 아니다

| | 1000명 부하에서 |
|---|---|
| 서버 다운 | **0회** |
| 시험 직후 상태 | **즉시 정상** |
| 사용자가 받은 것 | 31%만 카드, 나머지는 "이해하지 못했어요" |

**죽는 게 아니라 느려지다가 답을 못 주는 것**이고, 부하가 빠지면 바로 복구된다.
봇이 3.5초에 스스로 포기하고 가벼운 카드를 내보내는 설계가 **자기 보호**로 작동한다.

> 단, 측정은 **30초짜리 순간 부하**다. 1000명이 몇 분씩 계속되면 다를 수 있다 —
> 그건 확인하지 않았다.

---

## 2. ⚠️ 가장 중요한 발견 — 고장이 눈에 안 보인다

**이건 고쳐지지 않았다. 여전히 유효하다.**

카카오톡은 **5초 안에 답이 안 오면 그 답을 버린다.** 그래서 봇은 늦을 것 같으면
3.5초에 스스로 포기하고 "이해하지 못했어요 🤔" 라는 **정상적으로 생긴 카드**를 보낸다.

| | 실제 상황 | 사용자가 보는 것 | 개발자 모니터링이 보는 것 |
|---|---|---|---|
| 평소 | 정상 | 호텔 카드 | 정상 |
| **서버 과부하** | **69% 가 답을 못 받음** | **"이해하지 못했어요"** | **정상 (에러 0%)** |

**세 칸 모두 "정상" 으로 보인다.** 서버가 한계에 닿아도 오류가 하나도 기록되지 않는다.

기획 관점에서의 의미:

- **CS 에 "봇이 자꾸 못 알아들어요" 가 들어오면 AI 성능이 아니라 서버 부하일 수 있다**
- 이용자 이탈이 생겨도 장애 알림이 안 울린다
- **"이해하지 못했어요" 발생 횟수를 지표로 잡아야 한다.** 이게 늘면 증설 신호다

## 3. 무엇을 고쳐서 40배가 됐나 — 서버 증설이 아니다

**돈을 더 쓰지 않았다.** 병목이 세 군데였고, 하나씩 걷어냈다.

| 단계 | 병목 | 조치 | 결과 |
|---|---|---|---|
| 11-03 | **데이터베이스** | Supabase 무료 → OCI MySQL (둘 다 무료) | 20명 → 300명 |
| 11-04 | **서버 앞단 설정** | nginx 연결 수 제한 768 → 4096 | 300명 → 800명 |
| 지금 | 서버 자체 (CPU 1개) | — | 더 올리려면 비용 |

### 왜 서버 증설이 답이 아니었나

**11-02 에 서버를 5배 성능으로 교체했었다. 한계는 1도 안 움직였다.**

| | 이전 서버 | 5배 서버 | 변화 |
|---|---|---|---|
| 서버 자체 처리량 | 98건/초 | **505건/초** | **5배 ↑** |
| **챗봇 동시 사용자 한계** | 20명 | **20명** | **변화 없음** |

서버는 놀고 있었고, 진짜 범인은 **질문 하나당 데이터베이스를 7번 왕복**하는
구조에 데이터베이스가 **1초에 34건**밖에 못 받는 것이었다.

> 매표소 비유 — 창구 직원을 5배 빠른 사람으로 바꿨는데, 서류를 **창고에 7번
> 다녀와야** 하고 창고가 1초에 34번만 열린다. 직원을 아무리 빠르게 해도 줄은 안 준다.

**창고를 바꿨더니(MySQL 이전) 1초에 1,565건까지 받아도 멀쩡했다 — 46배다.**
그제서야 다음 병목(앞문 설정)이 드러났다.

## 4. ⚠️ 시험 도중 서버가 다운된 적이 있다 (10-27)

**이전 서버**에서 한계를 확인하려고 250명까지 밀어붙인 구간에서 **서버가 응답
불능이 되었고, 최소 43분간 다운됐다.** 수동 조치로만 복구됐다.

**이번(11-04)에는 1000명까지 밀었는데도 멀쩡했다.** 차이는 세 가지다 —
메모리가 6배, 자동 중단 장치를 켜둔 것, 복구 수단(SSH)을 미리 확보한 것.

기획 관점에서 알아야 할 점:

- **서버 전체가 멈추면 준비해둔 "점검 중입니다" 안내조차 못 나간다.**
  사용자는 봇이 아무 반응도 없는 상태를 본다
- **그 장애를 43분간 아무도 몰랐다.** 외부 감시 장치가 없다

## 5. 의사결정이 필요한 것

| # | 항목 | 내용 |
|---|---|---|
| 1 | **오픈 규모 상한** | 현 사양으로 **동시 800명**. 목표(100~300명)의 2.7배 여유 |
| 2 | **당분간 증설 불필요** | 현재 실사용이 하루 6~30건이다. 800명은 과잉 |
| 3 | **지표 추가** | "이해하지 못했어요" 발생률. **현재 유일하게 과부하를 알려주는 신호** |
| 4 | **장애 알림** | 서버 다운을 감지하는 외부 감시 필요. 지금은 아무도 모른다 |
| 5 | **인기 도시 관리** | 미리 검색해 저장해두면 그 도시는 빠르고 공짜. 프로모션 도시는 사전 준비 가능 |

**4번이 가장 시급하다.** 용량은 이미 충분한데, 문제가 생겨도 알 방법이 없다.

## 부록 — 용어

| 용어 | 뜻 |
|---|---|
| 동시 사용자 | 같은 순간 답을 기다리는 사람 수 (가입자 수가 아니다) |
| 응답 시간 | 질문 후 카드가 뜨기까지. 카카오 제한은 5초 |
| 캐시 | 한 번 검색한 결과를 저장해 재사용하는 것. 빠르고 공짜 |
| 폴백 | 제대로 답할 수 없을 때 대신 내보내는 안내 카드 |
