# 부하 시험

> 서버: Oracle Cloud `VM.Standard.A1.Flex` (OCPU 1 · RAM 6GB · ARM64 · 도쿄) · DB: Supabase · AI: OpenAI
> 대상: `https://bot.nolmoa.com` (Cloudflare → nginx → `127.0.0.1:8000`)

## 먼저 알아야 할 것 — 여기서 "못 버틴다" 는 500 이 아니다

카카오는 **5초를 넘긴 응답을 버린다.** 그 전에 앱이 스스로
`KAKAO_RESPONSE_BUDGET_SECONDS`(기본 3.5초)에서 끊고 도움말 카드를 보낸다.

그래서 서버가 한계에 닿아도 **HTTP 는 전부 200 이다.** 상태코드·에러율만 보는
평범한 부하 시험은 이 서비스의 고장을 통째로 놓친다. 사용자에게 보이는 고장은
"이해하지 못했어요" 라는 멀쩡한 카드다.

이 하네스가 상태코드가 아니라 **응답 본문을 분류하는** 이유다.

| 분류 | 본문 신호 | 뜻 |
|---|---|---|
| `card` | `listCard` | 정상. 저장된 결과가 나갔다 |
| `help` | `이해하지 못했어요` | 의도 불명(정상) **또는** 예산 초과 |
| `budget_cut` | `help` + 응답시간 ≥ 예산×0.9 | ⚠️ **진짜 고장.** 이것만 센다 |
| `searching` | `찾고 있어요` | 캐시 미스 — 백그라운드 검색 시작 |
| `busy` | `먼저 찾고 있어요` | 같은 키를 다른 요청이 선점 (부하에서는 정상) |
| `app_down` | `점검 중` | ⚠️⚠️ nginx 폴백. 앱에 **아예 못 붙었다** |

`help` 와 `budget_cut` 을 가르는 게 핵심이다. "안녕" 에 대한 도움말은 240ms 에
나오고, 예산에서 잘린 도움말은 3.5초를 꽉 채우고 나온다. 본문은 같고 시간이 다르다.

## 비용이 어디서 나는가

의도 해석은 3단이다 — **캐시 → 키워드+도시 사전 → 모델.**
`"오사카 호텔 추천해줘"` 같은 발화는 **2단에서 끝나 모델을 아예 안 부른다(0원·0ms).**

그러므로 부하 단계의 비용은 **검색 결과 캐시가 채워져 있는가** 에만 달렸다.

- `warmup.sh` 가 도시당 **한 번** OpenAI 웹 검색을 돌려 캐시를 채운다 ← 여기서만 돈이 든다
- 그 뒤 부하 단계는 DB 읽기 + CPU 뿐이다 ← **사실상 공짜로 무제한 반복 가능**

캐시를 안 채우고 부하를 주면 측정되는 건 서버 용량이 아니라 **OpenAI 대기열**이고,
비용은 요청 수만큼 나간다. 워밍업을 건너뛰지 말 것.

## 실행

```bash
# 1. 캐시 채우기 (도시당 OpenAI 1회. 2~3분)
./loadtest/warmup.sh

# 2. 기준선 — DB 도 AI 도 안 붙는 순수 앱 용량
BASE=https://bot.nolmoa.com VUS=20 k6 run loadtest/health.js

# 3. 본 시험 — 동시 사용자를 단계적으로 올린다
./loadtest/run.sh
STEPS="1 5 10 20 40 80" SCENARIO=cached ./loadtest/run.sh
```

`run.sh` 는 **자동으로 멈춘다**: nginx 폴백이 한 번이라도 나오거나, 예산잘림이
25%(`ABORT_HELP`)를 넘으면 다음 단계로 올라가지 않는다. 운영 서버이기 때문이다.

### 시나리오

| `SCENARIO` | 발화 | AI | DB | 무엇을 재나 |
|---|---|---|---|---|
| `nontravel` | "안녕하세요" | 0회 | 사용자 등록 | **바닥값.** 라우팅+DB 1회 |
| `cached` | "오사카 호텔 추천해줘" | 0회 | 사용자+장소+검색 | **주력.** 실사용 카드 경로 |
| `more` | "더 보기" 커서 | 0회 | 읽기만 | **최저가.** 저장된 행 자르기 |
| `mixed` | 위 7:1:2 | 0회 | — | 기본값 |

## 읽는 법

```
║ VU     req/s      p50      p95   예산초과     예산잘림   앱다운 HTTP실패 ║
║ 10      38.2    240ms    410ms      0.0%       0.0%        0    0.0% ║
║⚠40      41.1   1980ms   4120ms     14.2%       9.1%        0    0.0% ║
```

- **p95 가 3500ms 를 넘는 첫 단계가 답이다.** 그 위부터 사용자는 카드 대신 도움말을 본다
- `req/s` 가 VU 를 올려도 안 늘면 → 포화
- `health.js` 의 p95 는 멀쩡한데 라우터만 무너지면 → 범인은 DB 왕복이다.
  **실제로 그랬다** — 서버를 5배로 키웠는데 라우터 천장은 안 움직였다 ([결과](../docs/LOADTEST.md#3-병목은-서버가-아니다--서버를-5배로-키워-증명했다))
- `앱다운` 이 0 이 아니면 → 컨테이너가 죽었거나 OOM. `docker stats` 를 같이 볼 것

## 서버 쪽에서 같이 볼 것

부하 중 서버에서 돌려두면 "무엇이 먼저 무너지는지" 가 보인다.

```bash
docker stats --no-stream            # CPU 100% 면 1 vCPU 포화, MEM 1GB 면 OOM 임박
docker compose logs -f app | grep -E '예산|ms='   # 예산 초과 로그와 구간별 소요
```

## 한계

- **Cloudflare 를 통과한다.** 한 IP 에서 과하게 때리면 CF 가 먼저 막아 서버가 아니라
  CF 를 측정하게 된다. 오리진만 재려면 서버 안에서 `BASE=http://127.0.0.1:8000`
  (단, 부하 생성기가 같은 1 vCPU 를 나눠 쓰므로 수치가 보수적으로 나온다)
- **캐시 미스(AI) 경로는 이 하네스로 재지 않는다.** 20~30초짜리 백그라운드 작업이라
  동시성 측정 대상이 아니고, 요청 수만큼 돈이 나간다. 그쪽은 `searching` 비율로만 본다
